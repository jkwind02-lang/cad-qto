# 审批凭据契约（`qto-human-review-evidence/1.0`）

## 背景

在提交 `3ae0b15` 上复现：`recompute_qto_dependencies.py` 的 `approval.actor` 为空字符串、空格、数字、布尔值、列表、对象，或 `Claude`、`Claude Opus 5.5`、`Codex`、`GPT-6` 时，节点都被判为 `current`（已复核）；伪审批得到 `current` 后，下一轮即使删掉审批字段，只要指纹不变仍会继承 `current`。输出的 `business_adoption_allowed` 一直是 `False`，不会自动进入正式量；缺陷是无效或模型自填的审批能形成并继承"已复核"状态。

## A 期（已实现，0.3.0）

实现位置：`skills/_qto-shared-evidence/scripts/qto_human_review_evidence.py`（凭据核验）、`qto_actor_identity.py`（模型名称识别）、`recompute_qto_dependencies.py`（重算侧接入）。回归：`tests/test_approval_evidence.py`。

**审批字段**：计算输入节点的 `approval` 须有 `fingerprint`（完整计算指纹）、非空 `reviewer`、`reviewer_type: human`、带时区的 `reviewed_at`、`evidence: {path, sha256, record_id}`。旧格式只有 `actor` 的审批不再判为已复核，也不被批量升级为人工确认。

**凭据文件**：`{schema: "qto-human-review-evidence/1.0", project_id, records: [...]}`，每条记录：

| 字段 | 含义 |
|---|---|
| `record_id` | 本文件内唯一 |
| `reviewer`、`reviewer_type` | 实际复核者的非空姓名、固定 `human` |
| `reviewed_at` | 带时区的 ISO 8601 时间 |
| `decision` | 固定 `confirm_quantity` |
| `node_id`、`calculation_fingerprint` | 对应计算节点及其完整计算指纹 |
| `review_object_key`、`result_fingerprint` | 复核页对象键与该对象的成果指纹（不用全页指纹冒充） |
| `quantity`、`unit` | 用户确认的数值与单位 |
| `source_feedback` | 原用户批注文件的 `path`、`sha256`、`annotation_key`、`saved_at` |

**判定**：

- 节点审批要同时满足：字段合格；凭据文件存在且哈希一致；凭据属于同一 `project_id`；记录恰好一条；记录的复核者不是模型或助手名称，与审批填写一致；`decision` 为数量确认；节点、计算指纹、单位一致，数值与当前值一致；原批注文件存在且哈希一致，属于同一项目，对应批注的 `decision_type` 为 `quantity_confirmation`、复核者一致，并在 `quantity_confirmations[]` 中有与本节点、两种指纹、数值、单位都一致的确认项。
- 全部满足且指纹仍是当前指纹：`review_state: current`，输出 `review_evidence`（凭据绝对路径、哈希、记录编号、复核者、时间）供下次继承。
- 凭据合格但指纹已变：`stale`，列入 `stale_reviews`。
- 任一项不满足：`unreviewed`，在 `approval_issues` 写明原因，整体状态 `REVIEW_REQUIRED`。数量照常计算，不置零、不阻断其他节点。
- 继承上一轮的 `current` 时重新核验凭据：上一轮没有 `review_evidence` 的 `current` 不再继承（记为 `unreviewed` 并写原因）；凭据缺失、被改或不再对应的，降为未复核。
- 相对路径按输入文件（或上一轮结果文件）所在目录解析，原批注路径按凭据文件所在目录解析，不依赖进程当前目录。

**模型名称识别**（附加一层，不是人工复核的证明）：`ai`、`llm`、`model`、`assistant`、`bot` 等短词按完整词匹配，不误伤 `Wang Kai`、`Bai`；以 `claude`、`codex`、`gpt-`、`chatgpt` 开头，或等于 `anthropic`、`openai`、`gpt` 的视为模型；中文含"模型""助手""人工智能"等的视为模型。已知局限：名字本身以 Claude 开头的真人会被拒，需要换用能区分的填写方式。`build_pipe_inference_input.py` 和 `build_component_instances_from_neutral.py` 的裁决台账 `confirmed_by` 也改用这条共享规则；裁决台账是另一种来源契约，仍保持原有版本、来源和证据校验，不强行改成数量确认凭据。

**边界**：文件哈希只能证明内容一致，不能证明操作者身份。这是本地可追溯的复核契约，不据此宣称身份认证或正式数量采用；不为此增加账户、证书或新服务。模型继续自主识图和工作算量，凭据只用于用户主动做人工数量复核时；无审批的正常计算不受影响。

## B 期（待下一次独立维护会话）

复核页前端、反馈读取和复核契约的新功能，单独测试和发布，不阻塞移植：

- 现有页面对象保留 `object_id/catalog_key`，增加节点对应：单个数量用 `calculation_node_id`、`calculation_fingerprint`；同一实物有多个量时用 `calculation_bindings[]` 逐项绑定，绑定纳入对象成果指纹。
- `qto-review-feedback/2.0` 的 `annotations[批注键]` 增加可选的 `decision_type: quantity_confirmation`、实际填写的 `reviewer`、`reviewed_at` 和 `quantity_confirmations[]`（`node_id`、`calculation_fingerprint`、`review_object_key`、`result_fingerprint`、`quantity`、`unit`）。只有明确的"确认当前数量"操作写入这些字段；旧文件缺失时按普通意见处理。
- 只有当前节点绑定时才提供"确认当前数量"；先保存原批注文件，再计算其哈希并另导出凭据，不把带该文件哈希的凭据嵌回原文件。普通意见、整组方法意见、草稿、助手"已应用并复算"回执都不生成审批；组确认逐成员绑定，排除的成员不带入。
- 导入旧 HTML/JSON 时保留原批注；缺失数量确认或节点绑定的保留为意见并提示待复核，不根据 `confirmed_result` 的文字猜成数量确认，不由模型自填 `human`。
