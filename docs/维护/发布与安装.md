# 发布与安装

```text
插件仓库（唯一手工修改）
   │ 维护会话提交 → release_package.py build：按发布清单从该提交提取，生成发布记录
   ▼
发布目录（自动生成，只读）──► Claude 安装 → Claude 缓存（按发布记录核对）
                         └──► Codex 安装 → Codex 缓存（按发布记录核对）
                              两边都由发布宿主的 release-install 一次完成
```

开发调试不经过发布目录：测试直接在仓库里跑；Claude 用 `claude --plugin-dir <仓库>` 临时加载。

## 版本规则

- 改变实际安装包时递增业务版本（`+` 号前，如 `0.3.0`），先写清单再提交。`.codex-plugin/plugin.json`、`.claude-plugin/plugin.json` 和 `.claude-plugin/marketplace.json` 的业务版本必须一致，`tests/test_host_compat.py` 检查。
- 只改不入包的维护资料或测试，不强制升版本。
- 宿主后缀先不用；只有安装演练实际发现缓存未刷新时，才采用有证据的后缀，并登记为发布记录的允许差异。
- 一致性核对以"源提交号 + 运行文件哈希"为准，版本号只作标识。

## 发布包内容

- `运行文件清单.json` 列出的运行文件（条目 `path` 相对 `skills/`，提取时补前缀）。专业 references、assets 属于运行依赖。
- 根白名单（`release_package.py` 的 `ROOT_WHITELIST`）：两份插件清单、Claude 本地市场清单、`使用说明.md`、`运行文件清单.json`。`README.md` 不进包：它链接的 `docs/` 不发布；`使用说明.md` 是自包含的安装版说明，兼容测试核对发布包内所有 Markdown 相对链接都能在包内解析。
- 生成文件 `发布来源.json`：业务版本、完整源提交号、运行清单哈希、三份清单的版本。HTML 复核页优先读它的业务版本。
- `docs/维护/`、测试、基准、维护脚本、反馈服务留在仓库。

## 受测即所发

1. `python maintenance/release_package.py run-tests [--with-feedback-service] --model <模型>`：依次跑 compileall、pytest（JUnit）、HTML 契约、HTML 交互（有 node 时），记录到 `<插件维护>/受测记录/<受测指纹>.json`。受测指纹是仓库全部 Git 可见文件的逐文件哈希汇总；测试前后指纹不同则判为不可信。
2. 提交后用 `release_package.py fingerprint --commit <提交号>` 核对：与受测记录指纹相同即可复用，不机械重跑；任何字节变化补做受影响检查。
3. 推送前的 `pre-push` 钩子做同一核对。钩子不执行推送或部署。

## 发布前检查：交叉复测与发布错峰

提取（`build`）之前，下面三条都满足才发布（2026-10-15 用户定）：

1. **另一宿主交叉复测通过。** 改动属于[门禁与基准](门禁与基准.md)“交叉行为复测”范围的，由改动方以外的宿主复测：Claude 改的由 Codex 复测，Codex 改的由 Claude 复测。不能用改动方自测代替。复测回执的路径写进发布说明，也写进对应登记维护回写节的“交叉复测”行。不需要复测的改动，在提交信息里写明理由。
2. **发布错峰。** 发布前查在用项目有没有正在做的包，可以读项目的插件版本台账、进度文件或会话台账，查不清就问项目的问题收集会话或用户。有包正在做时不发布，等该专业本轮收尾后再发，包内不换版。
3. **发布说明。** 在发布记录旁写 `<插件维护>/发布记录/<业务版本>_<提交号前12位>_发布说明.md`，至少写明：
   - 本版包含的提交和登记；
   - 影响哪些专业和能力；
   - 需复跑哪些项目和包，与登记回写的“需复跑”一致；
   - 交叉复测回执路径；
   - 在用项目检查的结果，以及已收尾的专业。

   发布记录 JSON 冻结后不改，发布说明是给人看的补充，不代替发布记录。

## 提取与发布记录

```text
python maintenance/release_package.py build --commit <40 位提交号> --out <任务工作区内的临时目录>
```

- 工作区有未提交改动时拒绝（`--allow-dirty` 只用于演练）。
- 从 Git 对象读取每个文件，不复制工作区，也不直接把 `git archive` 当安装包。
- 三类检查：缺失（清单有、提取结果没有）、篡改（哈希与清单不符）、多余（不在清单和白名单里）。任一项不通过就删除临时包、不发布。
- 没有通过的完整回归记录时拒绝（`--allow-untested` 只用于演练，记录会标为未受测，`publish` 拒绝使用）。
- 发布记录写入 `<插件维护>/发布记录/<业务版本>_<提交号前12位>.json`：业务版本、完整源提交号、清单版本、运行清单哈希、受测指纹及测试摘要、允许差异、每个包文件的路径、SHA-256、大小和来源（运行清单、根白名单、生成）。记录用原子创建，冻结后不改；同一提交重复构建时内容必须一致。记录不把自己纳入哈希。

## 替换发布目录

```text
python maintenance/release_package.py publish --package <临时包> --record <发布记录> --target <发布目录>
```

先按发布记录核对临时包，再把当前发布目录移到 `<插件维护>/回滚包/`，复制新包并再核对；任何一步失败就恢复原目录。只需保留上一版回滚包，更早的回滚包按清理要求另行确认后处理（走回收站）。

## 两边安装核对（`maintenance/install_check.py`）

**一边发布、两边同步安装**（2026-10-16 用户定，登记 20261016-1229）：发布宿主在 `publish` 之后一次装好两边，不再写交接单请另一宿主安装。

```text
python maintenance/install_check.py init --record <发布记录>
python maintenance/install_check.py release-install --record <发布记录> --release-dir <发布目录> --rollback-release-dir <publish 保留的上一版回滚包>
```

- `release-install`：先检查持有维护锁（Codex 一半要用），再固定顺序执行 `claude-install`、`codex-install`，两步的安装、逐文件核对和新进程入口核对与下面单侧命令完全相同。两边都通过，记录总体为"双宿主发布完成"。
- 任一边失败（含安装前检查拒绝），立即整批回退：两边已动过的一侧都先离开"已安装并核对"，按 Codex、Claude 的顺序各自恢复到本次之前的状态；升级时用 `--rollback-release-dir` 把上一版换回发布目录（核对与原安装字节一致），再重装上一版并逐文件核对。哪一边恢复不了就记"恢复未完成"，绝不写成完成。运行经过写在安装核对记录的 `release_install` 节（执行者、顺序、各步结果、回退结果）。
- `release-verify` 重做两边核对；`release-rollback` 在发布后发现问题时整批回退，规则同上。
- 已开始的批次不能再跑 `release-install`（防止覆盖最初的恢复依据）；先 `release-verify` 或 `release-rollback`。
- 单侧命令保留，用于复核、单侧修复或另一宿主自行安装；每侧的失败恢复语义不变。
- 不变的：代码改动的交叉复测仍由改动方以外的宿主做（见“发布前检查”），只是安装改由发布宿主执行。
- 隔离演练：`release-install` 同样接受 `--claude-config-dir`、`--codex-home --codex-marketplace --codex-marketplace-root` 和 `--check-file`。2026-10-16 用真实 CLI 在隔离目录演练过首装、升级、整批回退、Codex 安装前拒绝后 Claude 连同发布目录一起退回四种情形，记录在插件维护目录 `项目验证记录\第四批甲_20261016\M3隔离演练\`。

单侧命令：

- `init --record <发布记录>`：在发布记录旁建 `<记录名>_安装核对.json`，两侧均为"待执行"。
- `claude-install --record R --release-dir D`：记录安装前状态（本插件的安装项、本地市场）；注册或更新本地市场 `cad-qto-local`（已有同名市场指向别处时拒绝，不覆盖）；安装或更新 `cad-qto@cad-qto-local`；逐文件核对 Claude 缓存（缺失、篡改、多余；宿主生成的非运行元数据须逐项列为豁免）；再用新的 CLI 进程加载，核对版本和 15 个入口。
- `claude-verify`：只重做核对。`claude-rollback`：撤销本次新装的插件和新加的市场；升级时给 `--rollback-release-dir`，工具把上一版换回发布目录（Codex 仍在用本次发布来源时拒绝单侧换）、重装上一版，并按安装前字节快照逐文件核对；不给回滚包就把这一步列为待办，状态记为"恢复未完成"直到做完。
- `--claude-config-dir <临时目录>`：在隔离的 `CLAUDE_CONFIG_DIR` 中演练，不碰正式安装。2026-10-14 已核实 Claude Code 2.1.296 的插件命令遵循该变量。
- `codex-install --record R --release-dir D`：通常由 `release-install` 调用，也可由任一持锁宿主单独执行。安装前核对冻结记录、完整包、实际市场来源；保存本插件的原版本、启用配置表及上一版运行包。通过正常 `codex plugin add` 安装，用实际缓存逐文件核对，并启动新的本地 app-server 做 `skills/list`，不创建模型任务。入口名称与数量从包清单推导，不只看安装命令成功。
- `codex-verify`：重验实际安装、缓存与新加载入口。`codex-rollback`：首次安装撤销本次插件和新注册市场；升级时从已核验的上一版运行包恢复共同来源，再正常重装原版本，仅恢复本插件配置表，不覆盖整份 `config.toml`。若 Claude 已使用共同新来源或该来源出现非本批次变化，拒绝单侧覆盖，记录“恢复未完成”，改用 `release-rollback` 整批回退。
- Codex 演练选项：`--codex-home H --codex-marketplace N --check-file C`。市场不存在时给 `--codex-marketplace-root M`，其 `.agents/plugins/marketplace.json` 必须含正确市场名与本地插件来源；不要给隔离市场取已有的 `personal` 同名，因为本机隐式个人市场仍可能优先匹配。`--rollback-release-dir P` 可复用发布工具保留的上一版包，避免额外复制。正式安装默认既有 `cad-qto@personal`。
- Codex 新包无需 README、docs 或维护说明；仍含 Codex 插件清单、专业入口及全部运行依赖。该结论以每次实际安装和入口发现核验为准，不能由目录外观推断。
- 只有两边都"已安装并核对"，记录的总体状态才是"双宿主发布完成"。等待另一宿主与真实失败分开记录；核对以每边实际缓存逐文件比对和新进程入口加载为准，不凭安装命令成功或另一边的结果推断。

## 失败处理

- 只要一边待执行、安装或核对失败，安装核对记录不得写成完成。失败时登记"发布未完成"：用 `release-install` 时工具已自动整批回退两边；单侧安装时先恢复本侧由本次改动的安装及配置，再用 `release-rollback` 处理另一侧。
- 安装前记录每边本插件的版本、启用状态和来源，只恢复这些具体项目，不回写整份旧全局配置。
- 首次安装没有上一版时，撤销本次新增安装，恢复原本未安装的状态。
- 回滚也要核对文件和新会话状态；回滚失败明确保留"恢复未完成"。
