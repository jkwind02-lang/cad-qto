# 门禁与基准

## 四层门禁

| 层级 | 何时 | 内容 | AI 花费 |
|---|---|---|---|
| 确定性回归 | 按受影响范围；运行逻辑或公共依赖发布前做完整相关回归 | pytest、HTML 契约与交互、`tests/test_host_compat.py`；反馈服务只在受影响时检验。远端 CI 在获授权推送后再跑，结果单独报告 | 不调用模型 |
| 双宿主加载 | 每次发布前 | Claude：`claude --plugin-dir <发布目录> plugin details cad-qto`，核对入口数量和名称；Codex：按实际安装检查入口 | 无 |
| 发布一致性 | 每次发布 | 提取三类检查、受测即所发、两边缓存逐文件核对、失败处理 | 无 |
| 交叉行为复测 | 改动可能影响识图或数量时 | 由改动方之外的另一个宿主，在已建立参照的基准上复测 | 约一次试点的花费 |

## 交叉行为复测的触发条件

- 需要做：SKILL 与 references 中的方法文字；识别、测量、推算、计数、规则相关的脚本逻辑；输出字段与状态判定。
- 可以不做：只改错别字或排版、只增加测试而不改运行文件。提交信息里写明不做的理由。

## 兼容检查（`tests/test_host_compat.py`）

两份插件清单与本地市场版本一致；15 个入口的 frontmatter 与末尾问题登记指引；运行清单与实际运行文件一一对应；发布包内 Markdown 相对链接在包内闭合；含非 ASCII 的 PowerShell 脚本带 UTF-8 BOM，并在本机可用的 pwsh 7 和 Windows PowerShell 5.1 下解析；审批契约接线；HTML 版本读取。

共享方法主体不得把宿主专有调用写成唯一可执行路径；README 的两套安装示例、明确的宿主适配说明可以出现 `$qto-*`、`/cad-qto:*`、宿主路径及工具名，不做全仓关键词禁令。

## 基准：先建参照，再评分

Claude 试点和 Codex 第四轮都不是标准答案。参照按三步建立：

1. **对已列对象复核**：两边结果的分歧对象全部回原图做证据复核；一致对象按比例抽样复核。
2. **分区独立查漏**：把原图按区域划分，每个区域独立检查两边都漏掉的对象。上一步只能检查双方已列出的对象，发现不了共同漏项。
3. **记入参照**：能由图纸唯一判定的，按 `maintenance/evaluate_takeoff.py` 的 `adjudicated_drawing` 记入参照；需要用户判断的单列。

报告口径：只完成抽样时报告抽样范围和结果，不推算成整图准确率；参照建立前两边对比只称"一致性检查"。基准数据（项目图纸、缓存、标注）放在插件维护目录的 `基准数据/`，不进仓库；已有项目权威原件的只记路径与哈希。

## 防线分工

- Git 钩子（`.githooks/`，每个克隆执行一次 `git config core.hooksPath .githooks`）：提交前检查维护锁并跑兼容测试；推送前核对该提交有通过的完整回归记录。钩子拦不住直接改文件。
- 直接改文件的兜底有三道：维护开工必查 `git status`；发布工具拒绝从有未提交改动的工作区发布；发布记录逐文件核对。
