## 2. 顶层

```json
{
  "schema": "qto-review-view/1.1",
  "...": "1.0 的全部字段不变",
  "sources": [{"id": "AUDIT-B03", "title": "审计清单 3#动力中心.xlsx", "sha256": "<64位>"}],
  "scenes": [],
  "objects": [],
  "comparison": {
    "display_terms": {"third_party": "清单"},
    "handler_labels": {},
    "nature_labels": {},
    "thresholds": {"difference_rate_alert": 0.2, "consistent_band": {"计量": 0.05, "计数": 0},
                   "count_units": ["台", "个", "套", "组", "座", "系统", "处", "根", "块", "只"]},
    "legacy_search_evidence": null,
    "dimensions": [],
    "sources": [],
    "items": [],
    "common_issues": [],
    "issues": [],
    "member_tables": []
  }
}
```

- **顶层 `sources`** 照旧是复核身份的一部分（`source_sha256` 由它算出），只放稳定的输入：图纸、第三方清单文件。**不要放每轮都会变的成果表**，否则每次重算都换身份，旧批注就导不进来了；成果变化由结果指纹跟踪（第 9 节）。没有图纸的视图，列第三方清单文件即可。
- `scenes` 可以为空。这时全部 `objects` 必须是 `kind: "unlocated"`、`scene_id: null`，页面不显示图面区。不允许为了过校验造空图页。
- 有 `comparison` 时 `objects` 可以为空（全部明细都是“本行即依据”时，见 5.1）。没有 `comparison` 时仍至少要一个对象。
- `comparison` 可以只有问题：`sources`、`items` 都为空、只有 `common_issues`、`issues` 时，页面只有“待解决问题”（第 14 节）。没有第三方数量的专业也能这样把待定事项交给用户。
- `nature_labels`：问题性质八类的显示名，可以换成专业自己的叫法（6.1 节）。
- `display_terms.third_party`：页面上“第三方”一词换成什么，例如“清单”。只改显示，数据取值不变（结论仍写 `第三方无量`，页面显示“清单无量”）。默认“第三方”。
- `handler_labels`：问题四类的显示名，可以换成专业自己的叫法（第 6 节）。
- `thresholds.difference_rate_alert`：“差异超阈值”筛选的初始百分比（小数，默认 0.2），页面上可以临时调，只影响筛选。
- `thresholds.consistent_band`：“一致”带宽的默认值，即差额率绝对值，写小数；`0` 表示须相等。有任何要按数字判结论的来源段时必填。
  - 可以写一个数，所有单位都用它。
  - 也可以按单位类别分写，如 `{"计量": 0.05, "计数": 0}`。这时须同时给 `thresholds.count_units`，列出按计数处理的单位；不在其中的单位都按计量。
  - 生成器按默认值判一致、多算、少算（5.4 节）。页面顶部显示这条规则，用户可以在页面上临时改容差。
- `legacy_search_evidence`：可选，只用于检索记录规则生效前交付的成果。规则指《通用成果字段与状态》“否定结论与检索证据”，提交 e63fe30。
  - 整份视图的成果都在规则生效前交付、不回头补检索记录时，写 `{"rule": "e63fe30", "note": "为什么不补"}`。
  - 写了以后，“图上无”的检索依据可以不全或没有，页面标“检索记录不全”（第 5 节）。
  - 规则生效后交付的成果不能用这一项。新旧成果混在一起时，分成两份视图。
- 没有 `comparison` 时，就是现在的复核页。

## 3. 维度 `comparison.dimensions`

```json
[
  {"id": "building", "title": "楼栋", "role": "overview",
   "values": [{"id": "3#动力中心", "title": "3#动力中心", "order": 3, "merged_from": ["3#动力中心（桥架、配管部分）"]}]},
  {"id": "division", "title": "分部", "role": "section",
   "values": [{"id": "030408", "title": "电缆"}, {"id": "030411", "title": "配管"}]},
  {"id": "category", "title": "品类", "role": "category", "values": [{"id": "电力电缆", "title": "电力电缆"}, {"id": "配电箱", "title": "配电箱"}]},
  {"id": "system", "title": "系统", "role": "filter", "values": [{"id": "电气系统", "title": "电气系统"}]},
  {"id": "package", "title": "计算包", "role": "technical", "values": [{"id": "E-3-1", "title": "E-3-1"}]}
]
```

- `role` 五种：
  - `overview` 总览卡片的维度，恰好一个；
  - `section` 列表分节的维度，最多一个；
  - `category` 成果里分节下再分的品类，最多一个；
  - `filter` 只用来筛选，个数不限；
  - `technical` 算量内部的划分（例如计算包号），不进筛选，只在详情的“技术来源”里显示。用户 2026-10-15 看样页时指出，“分包”筛选里是一串英文包号，对审核没有意义，还会被误读为分包单位。
- 值域封闭：条目、明细行、对象、问题上的维度值，必须在对应的 `values` 里；没带的显示为“未归”。
- `order` 可选，决定总览卡片和分节的顺序；没写的按 `values` 的顺序。
- 子单位并入所属楼栋（例如“（桥架、配管部分）”）由专业在数据里做好，原名记在 `merged_from`，界面不做合并。
- 问题的维度值可以是数组（一个问题涉及几栋楼）；条目、明细行、对象的维度值只能是单值。

## 4. 第三方来源 `comparison.sources`

```json
[{
  "id": "AUDIT",
  "kind": "审计清单",
  "title": "IDM 项目审计清单（电气系统）",
  "files": [{"title": "3#动力中心.xlsx", "sha256": "<64位>"}],
  "basis_note": "工作表“表10.2.2-16 分部分项工程清单与计价表”，只取电气相关项",
  "row_ids": ["AUDIT|3#动力中心|电气系统|11", "AUDIT|3#动力中心|电气系统|13"]
}]
```

- `kind` 取值：审计清单、招标清单、对方报量、甲方核定量、其他（选“其他”要在 `title` 写明）。
- `row_ids` 是这个来源全部条目的稳定编号，由专业从来源文件抽取，不能重复。生成器据此检查每一行恰好出现一次（C3-3）。
  - 编号要在来源内唯一。同一楼栋里有几个系统各自编序号时，只用“楼栋 + 序号”会撞号（电气实测有 66 组、155 行）。
  - 编号至少要带上系统，例如“来源|单位工程|系统|序号”。
- 来源文件的哈希进入条目结果指纹（第 9 节）。
- 可以有多个来源，同一工程内容写成一个对照条目，各来源并排（5.3 节）。
- 来源文件里的单价不抽取，也不进视图。

## 5. 对照条目 `comparison.items`

一个对照条目是“本次量”和各来源数量能对上的最小单位。本次量只写一份，各来源各写一段，放在 `third_parties` 里。

```json
{
  "id": "清单|3#动力中心|电气系统|93",
  "kind": "third_party",
  "ours": {"quantity_name": "配管长度", "unit": "m",
           "levels": {"确认量": null, "规则推算量": 1897.99, "方案暂估量": 287.55, "未决量": null},
           "total": 2185.54,
           "note": "末端支路全程穿管，其余只计出桥架段"},
  "third_parties": [
    {"source_id": "AUDIT",
     "rows": [{"row_id": "AUDIT|3#动力中心|93", "seq": "93", "code": "030411001001", "name": "配管",
               "features": "暗配 JDG20", "unit": "m", "quantity": 1934.9}],
     "unit": "m", "quantity": 1934.9,
     "difference": {"value": 250.64, "rate": 0.1295},
     "conclusion": "多算",
     "third_party_corrected": false,
     "disposition_note": "……",
     "redirect_to": [],
     "search_evidence": null}
  ],
  "dimensions": {"building": "3#动力中心", "division": "030411", "package": "E-3-2", "system": "电气系统"},
  "detail_rows": []
}
```

| 字段 | 要求 |
|---|---|
| `id` | 稳定编号，跨轮次不变，全视图唯一。单来源时可以用 `来源|楼栋|序号` 一类写法；多来源时建议用与来源无关的写法 |
| `kind` | `third_party`：至少一个来源段；`extra`：清单外新增，`third_parties` 为空数组 |
| `name`、`features` | 可选。`extra` 条目必须有 `name`（页面标题用）；`third_party` 条目没写时，页面取第一个来源段第一行的名称和特征 |
| `ours.unit` | 必填 |
| `ours.levels` | 键只能是《通用成果字段与状态》的四个数量层级：确认量、规则推算量、方案暂估量、未决量。值是数字或 `null`；没写的键按 `null`。`null` 是未计算，与 0 不同 |
| `ours.total` | 本次合计 = 确认量 + 规则推算量 + 方案暂估量，**不含未决量**；三项都是 `null` 时为 `null`。可以不写，生成器补上；写了就核对（C3-5） |
| `estimate_dominant` | “以暂估为主”标记，生成器按固定规则补：方案暂估量 > 0 且方案暂估量 ≥ 确认量 + 规则推算量（`null` 按没有）。专业写了就必须与规则一致 |
| `third_parties[]` | 每个来源最多一段，按 `sources` 的顺序排列 |
| `third_parties[].rows` | 这一段涵盖的来源行，可以多行：来源把同一内容拆成几行，或几项合成一行时，都在这里列全。每行 `row_id`、`unit` 必填，`quantity` 是数字或 `null` |
| `third_parties[].quantity` | 等于各行数量之和（同单位）。来源没给量写 `null`，不能补 0；只有部分行有量时，按有量的行求和，并写 `quantity_note` |
| `third_parties[].unit` | 与 `ours.unit` 不同时必须写 `unit_mismatch_note`，这一段不画对比条，不参与差额率排序，`difference` 写 `null` |
| `third_parties[].difference` | `{"value": 本次合计 − 该来源数量, "rate": value ÷ 该来源数量}`，专业给出，生成器只核对。来源数量为 0 时 `rate` 写 `null`。结论为一致、多算、少算时必填；其他结论可以写 `null`。结论为“第三方无量”且来源数量为 `null` 时，可以按来源数量 0 写：`value` 等于本次合计，`rate` 写 `null` |
| `third_parties[].conclusion` | 按来源分别下结论，只能取：`一致`、`多算`、`少算`、`第三方无量`、`图上无`、`缺图`、`归入他项`。前三种由生成器按默认带宽判，专业可以不写；写了必须与带宽判定相同（5.4 节）。页面可以按用户设的容差重新显示这三种。后四种由专业写，页面照显示 |
| `third_parties[].third_party_corrected` | 第三方条目本身有误、本次已按正确内容计算时写 `true`，并写 `correction_note`。这是标记，与结论并存（例如“多算”且“第三方条目有误已修正”） |
| `third_parties[].disposition_note` | 处置说明，可选 |
| `third_parties[].redirect_to` | 结论为“归入他项”时必填，列去向条目的 `id`，可以多个 |
| `third_parties[].search_evidence` | 结论为“图上无”时必填，见下表；视图声明了 `legacy_search_evidence` 的可以不全、只写 `note` 或为 `null` |
| `third_parties[].missing_drawing_note` | 结论为“缺图”时必填 |

`search_evidence` 沿用共享《通用成果字段与状态》“否定结论与检索证据”：

| 键 | 要求 |
|---|---|
| `drawings` | 必填。检索了哪些图纸、图页或布局 |
| `targets` | 必填。检索对象：图层、块名、文字关键词、表格、实体类型及常见写法变体 |
| `method` | 必填。中性取证包检索、原生 CAD 补读、PDF/OCR 文字检索或逐页查看；脚本检索写脚本位置 |
| `hits` | 必填，数字。为 0 也写 0 |
| `unread` | 可选。没能读取的部分 |
| `uncovered` | 可选。可能含该类对象但没查的图纸 |
| `record_ref` | 可选。项目里检索记录的位置 |
| `note` | 可选。文字说明，例如只记了查过哪些图 |

检索记录不全的，按共享规则不能写“图上无”，应作为未决事项处理。

唯一的例外是视图声明了 `legacy_search_evidence`：成果在规则生效前交付，问题收集会话 2026-10-15 定不回头补。这时：
- 检索依据缺项或为 `null`，不报错；
- 生成器在该段补 `search_incomplete: true`，并列进 `comparison_exceptions`（`检索记录不全`）；
- 页面在列表和详情里标“检索记录不全”，已有的检索依据、`note` 和处置说明照样显示；
- 这些段不转成未决或待确认，不计入顶部待解决计数。“待解决问题”末尾单列一组“检索记录不全”，默认收起，只作提示（第 14 节）。

### 5.1 明细行 `items[].detail_rows`

```json
{"id": "E-3-2#93-1", "area": "1F", "level": "规则推算量",
 "quantity": 859.41, "unit": "m",
 "basis": "末端支路 5 回路，回路路由长（水平直角距离＋竖向）合计",
 "drawing": "D0xx", "locator": "1F 配电平面", "relation": "对应", "note": "",
 "dimensions": {"package": "E-3-2"},
 "aggregation": "sum_members",
 "member_keys": ["电气回路|E-3-2|1AL1-WL3"], "member_table": "circuit"}
```

- `id` 全视图唯一；`level` 取四个层级之一；`quantity` 数字或 `null`；`unit` 必须与所属条目的 `ours.unit` 相同。
- `area`（楼层区域）、`drawing`、`locator`、`relation`（例如“对应”“对应-修正”“清单外新增”）、`note` 都是显示用的文字，可选。
- `aggregation` 三种：
  - `leaf`（默认）：本行就是最小依据，没有成员对象，`member_keys` 为空。没有图面数据的包都用这种；
  - `sum_members`：本行数量等于成员对象同名、同单位、同层级数量之和（C3-2），要写 `member_quantity_name`，指明合计成员的哪个数量项；
  - `declared`：有成员（供回图和下钻），但本行数量不由成员合计得出，要写 `aggregation_reason`。
- 成员就是 `objects`，`member_keys` 填对象的 `catalog_key`。逐回路台账的每一行都可以是一个对象：有回图坐标的用 `line` 或 `point`，没有的用 `unlocated`。
- 同一对象的同一数量项只能进一行明细（C3-4）。
  - 数量项按数量名区分。`sum_members` 行取 `member_quantity_name`。`declared` 行可以写 `member_quantity_name`，不写时取所属条目的 `ours.quantity_name`，两者都没有时按整个对象算。
  - 一条回路同时给电缆长度、电缆头、配管、穿线几个条目供数时，各行的数量名不同，不算重复。
- 同一数量项确需拆给几行时，在每个相关明细行写 `shared_member_split: [{"member_key": …, "share": 0～1, "basis": "拆分依据"}]`。同一对象同一数量项的各份额之和为 1，`sum_members` 合计时按份额计。

**已定不计 `excluded`**：已经按口径定为不计的量（例如定为二期的干线、图示取消的箱），不写成未决，而在明细行上标 `excluded`：

```json
{"id": "E-A-1#57", "area": "室外", "level": "方案暂估量", "quantity": 52.4, "unit": "m",
 "basis": "1F 变配电室 → 二期厂房，直角距离估",
 "excluded": {"rule_ref": "K5", "issue_id": "D01", "note": "图标二期，按 K5 本期不计"}}
```

- `note` 必填。`rule_ref`（口径决定单编号）和 `issue_id`（已关闭的个别问题或共性问题）至少写一个。
- `issue_id` 指向未关闭的问题时报错：口径没定的仍是未决，应挂在该问题上。
- `level` 写这部分量原来的层级，说明它是怎么得来的。`quantity` 是数字或 `null`，没算过的写 `null`。
- 已定不计的行：
  - 不进条目的各层级，也不进本次合计（C3-1）；
  - 不算“有未决量”“以暂估为主”（C3-9）；
  - 不使偏差归为依据不足（5.5 节）。
- 一个条目可以只有部分明细已定不计。
- 明细全部已定不计的条目，本次合计必须是 0：`确认量` 写 0（口径已定，本期为 0），其余层级写 `null`。
- 生成器在条目上补两个值：
  - `ours.excluded_quantity`：已定不计行中有数的之和，都没有数时为 `null`；
  - `ours.excluded_rows`：已定不计的行数。
- 成员对象照常可以挂在已定不计的行上，供下钻和回图，C3-2、C3-4 照常检查。

### 5.2 成员台账表头 `comparison.member_tables`

```json
[{"id": "circuit", "title": "逐回路台账",
  "columns": [{"key": "attributes.起点箱", "title": "起点箱"}, {"key": "attributes.回路号", "title": "回路号"},
              {"key": "quantities.水平长度", "title": "水平 m"}, {"key": "quantities.竖向长度", "title": "竖向 m"},
              {"key": "attributes.图纸", "title": "图纸"}, {"key": "source", "title": "定位"}]}]
```

`key` 只能取对象已有的字段：`id`、`title`、`status`、`source`、`detail`、`attributes.<名>`、`quantities.<数量项名>`。界面不另算。

### 5.3 多来源并排

- **对齐由专业做**：把各来源里说的是同一内容的行归到同一个条目。来源之间拆分口径不同（例如招标一行对应审计两行），就把两行都列进审计那一段的 `rows`。界面不自己猜哪些行对应。
- **对不上的照样显示**：某来源没有这项时，条目里只写有的来源段。列表里缺的那一列显示“无对应”，与“第三方无量”区分开：后者是来源有这一行，但没给数量。
- **列表一行**：本次量只显示一次，后面每个来源占一列，显示该来源数量、差额率和结论。只有一个来源时与单来源设计相同，不多出空列。
- **当前对照来源**：顶部选择器，默认是 `sources` 的第一个。按差额率或差额排序、“差异超阈值”筛选、总览卡片计数，都按当前对照来源算；切换来源不改数据。只有一个来源时不显示选择器。
- **筛选**“来源间结论不一致”：同一条目里各来源段的结论不全相同。只有一个来源时不显示。
- **详情**：各来源的行并排列出（序号、编码、名称、特征、单位、数量），下面是本次各层级数量和明细行。

### 5.4 一致带宽：默认值与页面容差

用户 2026-10-15 的答复：“第 1 项我选：页面可设容差，默认计量 ±5%、计数必须相等。”

- **哪些来源段按带宽判**：与本次同单位、来源数量不为 `null` 也不为 0、本次合计不为 `null`，且结论不是第三方无量、图上无、缺图、归入他项的段。
- **默认带宽**取 `thresholds.consistent_band`：
  - 写一个数时，所有单位都用它；
  - 分写成 `{"计量": b1, "计数": b2}` 时，单位在 `count_units` 里的用计数带宽，其余用计量带宽。
- **怎么判**：按数据算 `r = (本次合计 − 来源数量) ÷ 来源数量`，不用专业四舍五入后的差额率。
  - `b > 0`：`|r| ≤ b` 为一致；否则 `r > 0` 多算，`r < 0` 少算。
  - `b = 0`（须相等）：本次合计与来源数量在数值容差内相等为一致；否则按正负判多算、少算。
- **生成器**按默认带宽判：
  - 专业没写结论的，按判定写进数据；写了而与判定不同的，报错（C3-5），不允许逐条另判；
  - 在按带宽判的段上补 `band_check: {"rate": r, "equal": 本次合计与来源数量是否在数值容差内相等}`，供页面按容差重新显示，页面不再自己算比值。
- **页面容差**：
  - 顶部显示默认规则，例如“一致：计量 ±5%，计数须相等”。旁边可以改容差：分写时计量、计数各一个输入，否则一个。另有“恢复默认”。
  - 只有带 `band_check` 的段按页面容差重新显示一致、多算、少算。第三方无量、图上无、缺图、归入他项，以及单位不同、来源数量为 `null` 或 0 的段，照数据显示。
  - 与数据结论不同的段标出原结论，例如“多算（原：一致）”。
  - 总览计数、结论筛选都按页面显示的结论算。
  - 页面容差只在本页打开期间有效，不写回数据，不改指纹。保存的批注会记下当时的页面容差和显示的结论（第 9 节）。
- 来源数量为 0 而本次有量的，不按带宽判，由专业写“第三方无量”。
- 默认带宽或 `count_units` 改了，重新生成后受影响条目的结论随之改变，这些条目上的旧意见标为过期，因为结论在指纹里。页面容差只改显示，不使意见过期。
- “差异超阈值”筛选的百分比与容差是两回事，仍可以单独调，只影响筛选。

### 5.5 偏差归因：本次依据是否充分

用户 2026-10-15：“有偏差只是暴露出问题了……如果计算过程依据充分有偏差应该是清单的问题。”

- **对象**：结论为多算、少算、第三方无量、图上无的来源段。按数据结论归因，页面容差（5.4 节）只改显示，不改归因。
- **生成器在这些来源段上补 `attribution`**（固定规则，不是工程量）：
  - 先看本次依据是否不足：条目有方案暂估量 > 0，或有未决量（同 C3-9 的口径），或挂在未关闭的个别问题或共性问题上（直接挂，或经个别问题挂）。都不是，就是依据充分。
    - 性质为“清单的问题”（`list_issue`）的问题不算：它说的是清单错了，不说明本次依据不足。C3-9 和“依据不足的偏差未挂问题”判断有没有挂问题时，照常算它。
  - `list`：本次依据充分，偏差是清单的问题。
  - `ours`：本次依据不足，且差额绝对值不大于方案暂估量与未决量之和（同单位；`null` 按 0）。偏差可以由我方没算实的部分解释，归到所挂的问题上。
  - `both`：本次依据不足，但差额绝对值大于方案暂估量与未决量之和。生成器补 `excess` = 差额绝对值 − (方案暂估量 + 未决量)，即不确定部分解释不了、仍属清单的那部分。
  - 差额按 C3-5 的口径：图上无按本次 0，第三方无量按来源数量 0。单位不同、没有差额的段写 `attribution: null`，页面列进“无法归因”。
- **清单问题的类型**：`list`、`both` 的段按结论分：多算 → 清单少计；少算 → 清单多计；第三方无量 → 清单漏量；图上无 → 清单列了图上没有的。另外，有 `third_party_corrected` 的段都进“清单规格写错”一类（与上面的类型并存）。
- **隐含共性问题**：生成器为每个非空的类型补一条共性问题（6.2 节），编号 `清单的问题|<类型>`，性质 `list_issue`，处理方 `confirm`，问法固定为“本次依据充分、与清单不符的，按本次计，差异交清单编制方核对？”，现做法即“按本次计”。用户整组答复一次（第 9 节）。专业不能用 `清单的问题|` 开头的编号。
- `ours` 的段不另建问题，跟着所挂的问题走；`ours`、`both` 而条目没挂任何未关闭问题的（例如只因含暂估而依据不足），列进 C3-9 的提醒“依据不足的偏差未挂问题”。
- 一致、归入他项不归因。缺图的条目属于“缺图纸或资料”，在待解决问题里。
- 已定不计的明细行（5.1 节）不算依据不足。
  - 条目因已定不计而少于清单的，照常归因；依据充分时一般归“清单多计”。
  - 页面在这样的来源段上标“含已定不计”，并列出不计的量和依据。
- 用电气 20:28 数据按“依据充分 / 不足”两分试算（未细分 `both`）：782 条偏差中依据充分 518 条（多算 82、少算 53、清单无量 103、图上无 280），依据不足 264 条，其中 155 条只因含暂估、没挂问题。

## 6. 问题 `comparison.issues` 与共性问题 `comparison.common_issues`

问题指算量计算过程中发现的、使本次成果没有依据或无法判断的事项（用户 2026-10-15）。偏差只是把问题暴露出来，不是问题本身；与清单对比得出的“清单的问题”只是其中一类（6.1 节第 8 类）。

问题分两层，目的是答一类、解决一片：
- **共性问题**：一类问题的统一问法，答复是一条口径或规则。答复一次，挂在下面的个别问题和条目一起生效。
- **个别问题**：具体出现在某栋楼、某个包、某些清单项上的问题。能归到共性问题的写 `common_issue_id`，自己不用再单独答复；归不进去的单独成立，自己就是一条要答复的问题。

专业提问时先想“这个口径别处会不会也遇到”。会遇到的写成共性问题，各处出现的写成它下面的个别问题，或直接把条目挂到共性问题上。电气已有的口径决定单（K1、K5、K8 等）就是这种做法：一条口径管很多处。

### 6.1 问题性质 `nature`

| 代码 | 默认显示名 | 你给的答复 | 一次答复覆盖 |
|---|---|---|---|
| `rule_gap` | 现行规则无法判断 | 定一条计算规则 | 全部同类内容 |
| `multi_method` | 有多种判断方式 | 在列出的做法里选一种，或另写 | 全部同类实例 |
| `missing_info` | 缺图纸或资料 | 给资料；或定“缺这类资料时怎么处理”的兜底口径 | 兜底口径覆盖所有缺同类资料的 |
| `drawing_conflict` | 图纸矛盾或不清 | 定取舍顺序（以哪种图为准、标注还是量取为准），或请设计确认 | 全部同类矛盾 |
| `scope` | 范围、分期或专业界面不清 | 定计、不计或列清单外 | 全部同类范围 |
| `assumption` | 按假设或估算计入 | 接受该估算方法（作方案暂估），或要求补资料 | 用同一方法估的全部实例 |
| `tool_limit` | 工具或方法限制 | 接受近似，或等插件改进 | 用同一方法的全部实例 |
| `list_issue` | 清单的问题 | 确认“本次依据充分，按本次计，差异交清单编制方” | 同一类清单差异 |

- 性质说的是“为什么不确定”，决定要什么样的答复；`handler` 说的是“需要谁做什么”。两者并存。
- 共性问题必须写 `nature`。挂了共性问题的个别问题取共性问题的性质，自己写了就必须相同；单独成立的个别问题应当写，没写的页面放进“未分类”，生成器提醒（C3-9）。
- 显示名可以用 `comparison.nature_labels` 换。
- `tool_limit` 类问题同时应在插件维护目录登记（《插件问题登记》），登记编号写在 `plugin_issue_ref`（可选），页面显示。
- `list_issue` 类一般由生成器按 5.5 节自动归出；专业也可以手写，例如清单漏列一整类、清单拆分口径与图纸不同。

### 6.2 共性问题 `comparison.common_issues`

```json
{"id": "G03", "nature": "multi_method",
 "question": "图示型号或规格与清单不一致时，怎么挂项",
 "text": "3# ZBN 与 ZB、接地连接线 BV-1*95 与 BVR-1x25、A/B 区同类灯具挂项口径不一致，都是这一口径",
 "options": [
   {"id": "O1", "text": "按图示规格挂最接近的清单项，型号差异记“清单有误已修正”", "impact": null},
   {"id": "O2", "text": "严格按清单型号，型号不同的列清单外新增",
    "impact": [{"value": 1520.0, "unit": "m", "note": "电缆约有这么多改列清单外"}]}],
 "current_option": "O1",
 "handler": "decide",
 "item_ids": [],
 "dimensions": {"building": ["A-晶圆厂房", "3#动力中心"]},
 "rule_ref": "K8",
 "status": "待定"}
```

- `question` 必填，写一般问法，不写具体某栋某项；`text` 写情况。
- `options`：
  - `multi_method` 必须至少两项；其他性质可选，例如范围类写“计 / 不计 / 列清单外”，假设类写“接受 / 要求补资料”。
  - 每项 `id`、`text` 必填；`impact` 写法同个别问题的 `impact`（`null`、一段或多段），是专业算好的“选这个做法与现做法差多少”。页面只显示，不求和。
  - 有 `options` 时 `current_option` 必填，指现在按哪个做法算。
- `handler`：四个代码同个别问题。`closed` 表示口径已经定了（写 `rule_ref`），只留记录。
- `item_ids`：没有个别问题、直接归到这条口径下的条目，例如用同一估算方法的全部条目。
- `rule_ref`：项目口径决定单里的编号。用户答复后，专业把答复记进口径决定单；下一轮或别的包遇到同类，挂到同一条共性问题（或在个别问题上写 `rule_ref`），不再重新问。
- **适用范围**（页面显示，也进指纹）= 挂它的个别问题，加这些问题挂的条目，加它自己的 `item_ids`，去重。

### 6.3 个别问题 `comparison.issues`

```json
{"id": "A01", "handler": "decide", "nature": "rule_gap", "common_issue_id": null, "plugin_issue_ref": null,
 "title": "引下线：内柱“上下贯通”接地线是否计入",
 "text": "各楼接地平面在内柱上画了“上下贯通”接地线……",
 "impact_text": "A 第 291 项若只计外侧柱为 681.0 m（本次 1439.2 m，清单 1429.66 m）……",
 "impact": null,
 "current_practice": "A、B、3# 计入内柱",
 "item_ids": ["清单|A-晶圆厂房|电气系统|291"],
 "dimensions": {"building": ["A-晶圆厂房", "B-封装厂房"]},
 "source_refs": [{"ref": "E-A-FFU-Q02", "text": "原条目原文……"}],
 "group_id": null, "status": "待定"}
```

- `handler` 取四个代码：

  | 代码 | 默认显示名 | 页面 |
  |---|---|---|
  | `decide` | 需要你定口径 | 展开 |
  | `confirm` | 需补资料或确认 | 展开 |
  | `assumed` | 已按假设计入 | 展开 |
  | `closed` | 已处理，仅留记录 | 默认收起 |

  显示名可以用 `comparison.handler_labels` 换成专业的叫法，例如 `{"decide": "需要你定口径（会改数量）", "confirm": "需设计、业主或清单编制方确认"}`。
- `title`、`text` 必填。`impact_text` 是影响的文字说明。
- `impact` 可选，只显示，不参与任何合计：
  - 写一段时为 `{"value": 数字或 null, "unit": "m", "note": "…"}`；涉及几个单位时写成多段数组；
  - `value` 有数字时须有 `unit`，为 `null` 时须有 `note`；
  - 定性影响可以只写 `impact_text`，`impact` 写 `null`。
- 一个问题涉及多个包时只写一条，原各包编号放在 `source_refs`。`source_refs` 每项可以是编号文字，也可以是 `{"ref": 编号, "text": 原文}`。
  - 要保留合并前各原条目的原文时用 `{"ref", "text"}`。例如电气 171 条原条目合并成 88 条，原文都放这里，满足不删减。
  - 表格输入用 issue_sources 表。
  - 电气意见第 8 处建议的 `source_texts` 与此作用相同，不另设字段。
- `item_ids` 可以为空（清单外或整体性问题）。生成器从 `item_ids` 反向建索引，条目详情里显示挂在它身上的问题。
- `group_id` 可选，连到现有问题组，以便回图。`status` 可选，只显示。
- `current_practice` 写“现在是怎么算的”。`decide`、`assumed` 两类建议必写，用户据此判断要不要改；不写时页面显示“未写现做法”。
- **涉及量**：页面在每条问题下按 `item_ids` 逐条列出挂接条目的本次各层级数量（确认、规则推算、方案暂估、未决）和合计，只显示各条目已有的数，不跨条目求和。
- 问题批注的快捷结论显示为“按现做法”“不按现做法”“暂不定”，数据里仍存 `同意`、`要改`、`待定`（第 9 节）。选“不按现做法”时，原因里写明应该怎么算。
- `common_issue_id`：所属共性问题。挂了的，用户答复共性问题后它自动按共性答复处理，页面上只能“设为例外”（第 9 节）。
- `rule_ref`：可选。已经按口径决定单某一条处理的，写编号，页面显示“已按口径 K… 处理”。
- 个别问题也可以有 `options`、`current_option`（写法同 6.2 节）；`multi_method` 类单独成立的个别问题必须有。

## 7. 网址定位

| 片段参数 | 作用 |
|---|---|
| `#item=<条目 id>` | 打开成果，选中该条目并回图；同时给了 `#mode` 且该模式里有这个条目时，在该模式里打开 |
| `#issue=<问题 id>` | 打开待解决问题，选中该个别问题 |
| `#common=<共性问题 id>` | 打开待解决问题，选中该共性问题（含隐含的 `清单的问题|…`，这时打开对照审核） |
| `#group=<问题组 id>` | 复核视图的问题组模式 |
| `#object=<catalog_key 或对象 id>` | 复核视图的对象模式 |
| `#scene=<图页 id>` | 切到该图页 |
| `#dim=<维度 id>:<值 id>` | 总览进入该维度值 |
| `#source=<来源 id>` | 切换当前对照来源 |
| `#mode=results\|resolve\|audit\|review` | 指定模式：成果、待解决问题、对照审核、图面复核；`issues` 作为 `resolve` 的别名，`extras` 打开成果并筛到清单外新增 |

- 几个参数用 `&` 连接，值用 `encodeURIComponent` 编码。
- 只在页面内的数据里查找。找不到时顶部提示“未找到 …”，停在默认视图，不报错。
- 同一页内改片段（例如点了页内链接）时，监听 `hashchange` 照样响应。
- 选中目标后用 `history.replaceState` 更新片段，复制地址栏就能分享当前位置。
- 不联网、不执行片段内容、不把片段写进 HTML 结构。
- 外部文件引用写法：`工程量图面复核_E-3-2_r1.html#item=%E6%B8%85%E5%8D%95%7C...`（整段 `encodeURIComponent`）。

## 8. 无图纸与图面区收起

- `scenes` 为空时不渲染图面区，列表和详情铺满整页。
- 有图页时，当前选中的条目、问题或对象没有任何可定位成员，图面区自动收起，详情和明细表加宽；切到有定位的目标时自动恢复。
- 顶部提供“图面：自动 / 展开 / 收起”开关，手动选择在本页打开期间一直有效。
- 《HTML交互复核与批注》第 3 行“不强制建立虚构图页”与原契约“至少一张图页”相矛盾，按本节改正（1.1 起允许无图页；1.0 仍要求图页，不变）。

## 9. 审核意见与闭环

- 新增三种批注键：`对照条目|<item id>`、`问题|<issue id>`、`共性问题|<common issue id>`。记录分别带 `item_snapshot: {item_id, result_fingerprint}`、`issue_snapshot: {issue_id, result_fingerprint}` 或 `common_issue_snapshot`（9.1 节），以及记录本身的 `result_fingerprint`。
- 快捷结论 `verdict` 取：`同意`、`要改`、`待定`，可以不填。问题批注上这三个值分别显示为“按现做法”“不按现做法”“暂不定”（第 6 节），条目批注上照原样显示。已保存的批注**必须写原因**；选了快捷结论的，结论文字可以留空，读取时以快捷结论为结论；没选快捷结论的，结论文字必填（与现有规则相同）。
- 条目批注可以取消勾选个别明细行，记在 `excluded_detail_row_ids`，只能是本条目的明细行。
- 条目批注另记 `page_view: {"consistent_band": 当时的页面容差, "conclusions": {来源 id: 当时显示的结论}}`，页面容差等于默认值时也记。它只说明审核人当时看到的结论，不参与过期判定，读取程序原样带进 `item_actions`。过期判定仍绑数据原结论和结果指纹。
- 草稿、保存、修改历史、合并导入、保存带批注 HTML、导出 JSON 都沿用现有机制。
- **结果指纹**（生成器重算，不信任传入值）：
  - 条目指纹覆盖：各来源段的行（编号、编码、名称、特征、单位、数量）、该来源文件哈希；本次各层级数量、单位、合计；各来源段的数量、差额、结论、修正标记与说明、处置说明、去向、检索依据、缺图说明；明细行（编号、数量、层级、单位、依据、聚合方式、成员、拆分、已定不计）；成员对象的指纹；维度值。
  - 问题指纹覆盖：处理方分类、性质、所属共性问题、标题、正文、影响、做法及现做法、现在的做法、关联条目。
  - 共性问题指纹见 9.1 节。
  - 任何一项变了，旧意见标为过期（stale），旧的数字确认不能继承；条目或问题不在了标为 unmatched。视图总指纹纳入这两类指纹。
  - 页面标题、`revision`、显示用语、“差异超阈值”筛选值、页面容差变化，都不使意见过期。默认带宽变化只通过改变的结论使相关条目过期（5.4 节）。
- `read_qto_review_feedback.py` 输出新增 `item_actions`、`issue_actions`，每条带编号、快捷结论、结论、原因、例外明细行、更新时间，以及“供所属专业复核；未自动写回数量”。
- `receipts` 的键同样支持 `对照条目|…`、`问题|…` 和 `共性问题|…`，回执沿用 `source_annotation_updated_at` 与 `source_result_fingerprint` 双重绑定。

### 9.1 答一类、解决一片：共性答复、继承与例外

用户 2026-10-15：“最好是我给出了某类问题的答案就能解决一片类似问题，而不是每一个问题单独回答。”看样页时还指出，逐条清单写意见“会产生很多重复的无效审核意见以及互相矛盾的审核意见”。

- **共性问题批注**：键 `共性问题|<id>`（含隐含的 `共性问题|清单的问题|<类型>`），带 `common_issue_snapshot: {common_issue_id, result_fingerprint, scope: {issue_ids, item_ids}}`。
  - 快捷结论同问题批注：按现做法、不按现做法、暂不定。
  - 选“不按现做法”时，从 `options` 里选另一个 `option_id`，或在结论里写新口径；原因必填。
- **继承**：共性答复对适用范围内全部个别问题和条目生效。这些个别问题和条目不用再单独答复：页面上它们显示“已按共性答复（G03：按现做法）”，没有快捷结论按钮，只有“设为例外”。
- **例外**：
  - 个别问题或条目的批注写 `exception_of: <共性问题 id>`，原因必填，说明这一处为什么不按共性答复、应该怎么算。
  - 例外的快捷结论和所选做法与共性答复相同时，页面提示“与共性答复相同，不必单独写”，不保存。
  - 共性问题还没答复时不能设例外，页面提示先答共性问题。
- **适用范围变了**：
  - 共性问题的问法、正文、性质、做法及影响、现做法、处理方变了，旧答复过期，要重答。
  - 只是适用范围变了（例如下一轮电气又挂进来几条），答复不过期，自动覆盖新实例；页面在该共性问题上标“答复后新增 N 处”，列出新增的个别问题和条目，读取程序输出 `added_since_answer`，供用户抽查。
  - 个别问题或条目自己的数变了，只使它们自己的例外批注过期，不影响共性答复。
- **不在任何共性问题下的**：单独成立的个别问题照现在的问题批注答复；条目批注只用于条目自己的问题（例如数据写错），在对照审核里，条目只在清单问题分组下整组答复，条目上只能设例外（第 14 节）。
- **冲突**：
  - 合并导入时，同一个键有两条不同的现行意见（快捷结论或所选做法不同），不自动取最新：页面标“意见冲突”，读取程序列进 `conflicts`；用户重新保存其中一条才消除。
  - 只有现行意见之间才算冲突。一方已过期或不再对应（例如旧一轮成果上的答复）时，保留现行的一方，过期的进历史并标 `conflict_from_merge`；过期一方的保存时间再新，也不能遮住现行意见。合并顺序不影响结果。
  - 冲突记录每次读取都按当前视图重新判定候选：页面打开和读取程序用同一规则。现行的不同意见不足两种时冲突消解，取现行的那条（没有现行的取最新），其余进历史。
  - 冲突候选里有例外（`exception_of: G`）时，用户重新保存其中一条之前，那一处不继承 G 的答复：页面显示“例外意见冲突”，读取程序把它从 G 的适用范围和带 `via` 的动作里去掉，在 G 的 `common_issue_actions` 上列进 `held_by_conflict: {issue_ids, item_ids}`。两条候选指向不同的共性问题时，两处都这样处理。
  - 同一条目落在两条共性问题的适用范围里，而两处答复一个“按现做法”、一个“不按现做法”时，页面提示“同一条目有两处答复，请核对”，读取程序列进 `overlaps`，只提醒。
- **读取输出**：
  - 新增 `common_issue_actions`：每条带编号、性质、快捷结论、所选做法、结论、原因，以及展开后的适用范围（`issue_ids`、`item_ids`，已除去例外和例外冲突中的各处）和 `added_since_answer`；有例外冲突时另带 `held_by_conflict`。
  - `issue_actions`、`item_actions` 里由共性答复带来的标 `via: <共性问题 id>`，例外标 `exception_of`。
  - 都只是用户意见，供所属专业复核；不自动写回数量。专业按答复重算后，把共性问题改为 `closed` 并写 `rule_ref`。
- **共性问题指纹**覆盖：性质、问法、正文、做法及各自影响、现做法、处理方。适用范围单独记在快照里，用于算“答复后新增”，不进过期判定。隐含共性问题的指纹覆盖类型和问法。

## 10. 生成器双向校验

任何一项不通过，生成器都返回 `INPUT_REQUIRED` 和具体条目，不出半成品页。所有显式声明的例外，都列在 `HTML生成检查.json` 的 `comparison_exceptions` 里。

| 编号 | 检查 | 方向 |
|---|---|---|
| C3-0 | 编号唯一：条目、明细行、问题、来源；来源段的 `source_id` 存在；维度角色个数合法；维度值都在值域内；`consistent_band` 是非负数，或分写的计量、计数两个非负数并有 `count_units`；`legacy_search_evidence` 有 `rule` 和 `note` | 结构 |
| C3-1 | 每个条目各层级的本次量，等于其明细行同层级数量之和，已定不计的行不计入；明细全部已定不计的条目本次合计为 0（5.1 节）；明细行的单位与条目单位相同 | 条目 → 明细行 |
| C3-2 | `sum_members` 明细行的数量，等于成员对象指定数量项（同单位、同层级，按拆分份额）之和；`declared` 有原因；`leaf` 没有成员 | 明细行 → 成员 |
| C3-3 | 每个来源的 `row_ids` 与各条目中该来源段 `rows` 里的行一一对应，不漏、不重、不越界 | 来源 ↔ 条目 |
| C3-4 | 同一成员对象的同一数量项（按数量名）最多进一行明细（跨条目也算）；拆分的份额合计为 1 | 成员 → 明细行 |
| C3-5 | 每个来源段的结论与字段自洽：归入他项有 `redirect_to`、目标存在且不是自己；图上无有完整检索依据（声明了 `legacy_search_evidence` 时不全只提醒，标检索记录不全）；缺图有说明；第三方无量时该段数量是 `null` 或 0；修正标记有说明；同单位且有差额时，差额 = 本次合计 − 该段数量、差额率 = 差额 ÷ 该段数量；一致、多算、少算与默认带宽判定相同（5.4 节），按带宽判的段必须有差额，带宽缺失时报错；`ours.total` 与各层级一致；`estimate_dominant` 与规则一致 | 条目内部 |
| C3-6 | 问题引用的条目、维度值、问题组、共性问题都存在；`handler` 合法；`nature` 是八个代码之一，挂了共性问题的与共性问题相同；`impact` 为 `null`、一段或多段，每段有数字时有单位、为 `null` 时有说明；有 `options` 的同 C3-10 | 问题 → 条目 |
| C3-7 | 对象带维度值时，与其所属条目一致；不一致的在对象上写 `dimension_mismatch_note` | 对象 ↔ 条目 |
| C3-8 | 每个条目每个来源最多一段；来源段数量等于其各行数量之和（部分行无量时有 `quantity_note`）；`extra` 条目没有来源段 | 来源段 ↔ 行 |
| C3-9 | **只提醒，不拦**：有未决量、以暂估为主、或有来源段结论为“缺图”的条目，都应挂在某个未关闭（`closed` 以外）的问题上；没挂的列进 `comparison_exceptions`（`不确定条目未挂问题`），报告给出条数，页面在“待解决”里标“未挂问题”。生成器在每个条目上补 `uncertain`（“有未决量”“以暂估为主”“缺图”标签数组）和 `uncertain_unlinked`，供页面分组；“有未决量”指未决量不为 `null`、0，或有未决量层级的明细行（已定不计的行不算）。同样只提醒的还有：本次依据不足的偏差未挂问题（5.5 节，`依据不足的偏差未挂问题`）；单独成立的个别问题没写性质（`问题未分性质`） | 不确定内容 → 问题 |
| C3-10 | 共性问题：编号唯一，且不与个别问题重号，不以 `清单的问题|` 开头；`nature` 合法；`question` 必填；`multi_method` 至少两项做法；有做法时 `current_option` 是其中之一，做法编号在本问题内唯一；做法的 `impact` 写法同 C3-6；`item_ids` 的条目存在；`handler` 合法 | 共性问题 → 条目 |
| C3-11 | 归因（5.5 节）：生成器重算 `attribution`、`excess`，数据里带了的必须与重算相同；隐含共性问题由生成器补，数据里不能预先写 | 来源段 → 问题 |
| C3-12 | 已定不计（5.1 节）：`note` 必填；`rule_ref`、`issue_id` 至少一个；`issue_id` 存在且已关闭（`closed`）；明细全部已定不计的条目，`确认量` 为 0、其余层级为 `null`；`excluded_quantity`、`excluded_rows` 由生成器补，数据里带了的必须与重算相同 | 明细行 → 问题 |

数值相等的容差为 `1e-6 × max(1, |值|)`。差额率允许专业四舍五入到 0.1%（小数容差 0.0005，含边界），例如表里写 `-61.4%`、按数据算是 −0.61424，算一致；按数据算是 0.3145、表里写 `31.4%` 也算一致。`null` 只能和 `null` 相等，不能当 0 用；唯一的例外是“第三方无量”的差额按来源数量 0 核对（第 5 节）。

### 11.1 页面载荷（2026-10-16 起）

用户要求在保留细节效果的前提下尽量降低页面大小。办法是只改页面里的传输编码，视图 JSON 和各字段不变，一处细节都不删。

- **格式**：页面 `<script id="payload">` 是 base64 编码的 gzip 数据，解压后有两种：
  - 普通 JSON：旧页面，以及没有可打包底图的页面；
  - 打包格式：`QTOPACK1`（8 字节）+ JSON 长度（4 字节，大端）+ JSON + 底图二进制。JSON 里各底图集（`background_sets` 的各项、场景自带的 `background`）留空数组，另加 `background_pack`：
    - `format`：`qto-background-pack/1`；
    - `styles`：共用样式表，是图元除坐标外的全部字段，含 `kind`、文字和字高；
    - `collections`：每项写 `set` 或 `scene`（场景序号）、`count`、`decimals`、`start`、`end`。
  - 二进制部分：每个图元依次写样式序号、点数（0 表示单点 `point`）、各点坐标。坐标先乘 10^`decimals` 化成整数，再与上一点相减，按 zigzag 变长整数写入。
- **无损**：
  - 一个底图集要打包，须满足：全部坐标在 6 位小数以内能精确还原，每个图元都只有 `point` 或只有 `points`，每个点都是两个有限数。不满足的那一集照旧写 JSON。
  - 生成器写出前先解包，与视图逐项比较，不相等就不出页面。
  - 页面解包时，长度对不上就报“底图打包数据不完整”或“长度不符”，不显示半截底图。
- **实测**：E-A-LGT 全包。
  - 页面 6.20 MB 降到 2.79 MB；E-A-CBL2 0.86 MB 降到 0.48 MB；E-S3 0.55 MB 降到 0.33 MB。
  - 真实浏览器就绪 1.04 秒降到 0.63 秒。
  - 抽 5 张图页比对新旧页面，画布逐像素相同。
- **剩下的大头**：E-A-LGT 载荷压缩后约 1.97 MB，其中对象约 0.45 MB，对象的成果指纹约 0.61 MB，底图约 0.68 MB。缩短指纹会改变批注绑定规则，要动契约，留给用户定。
- **报告**：`size_estimate` 加两项，`payload_gzip_bytes`（实际载荷）和 `background_packed`。

- 路径相对映射文件。CSV 一律 UTF-8（可带 BOM），第一行是列名。
- `columns` 把下表的标准键映射到项目列名；**列名和标准键相同的可以不写**。`constants` 给整张表写固定值。`value_maps` 按标准键做取值替换。`list_separators` 声明哪些列是多值、用什么分隔（默认 `;`）。
- 映射写了、转换却不认识的键不静默丢掉：`columns`、`constants`、`value_maps`、`list_separators` 里不是这张表标准键的（含没在 `comparison.dimensions` 声明的 `dim.*`），以及表一级不认识的字段（成员表另认 `quantities`、`attributes`），都列进检查报告的 `mapping_warnings`（位置、键、说明），只提醒、不拦生成。起因：问题收集会话 2026-10-15 转来，电气曾以为新列被静默丢掉，看不出 `issues_without_nature` 偏高的原因。
- 数字列：空白为 `null`；带 `%` 的按百分数换成小数；其余不能解析的报错，不猜。
- 是否列（`third_party_corrected`、`estimate_dominant`、明细表的 `excluded`）：`是`、`true`、`1`、`Y` 为真，空白和 `否`、`false`、`0`、`N` 为假，其他值报错。
- 维度 `values_from`：`"data"` 表示取数据里出现过的值（按首次出现顺序）；或者指向一张表，给出值列和可选的 `title`、`order`、`merged_from` 列（同一值多行时 `merged_from` 合并）。也可以直接写 `values`。
- 来源 `row_ids_from: "items"` 表示该来源的 `row_ids` 取各条目该来源段的行编号；这时 C3-3 只能查出重号，查不出漏行，报告里会写明。能从来源文件独立抽取时，用 `row_ids_table` 指向一张单列表，C3-3 才是真正的双向检查。两种写法：
  - 标准写法是对象 `{"path": "review_data/source_row_ids.csv", "column": "row_id"}`，`column` 可省，默认 `row_id`；
  - 也可以直接写路径字符串，按 `{"path": 该字符串, "column": "row_id"}` 处理。
  - 写成其他类型的报中文错误，并给出这两种写法。电气 2026-10-15 按字面写成字符串时报了 `TypeError`，问题收集会话定两种都认。

### 12.2 标准键

**items（对照条目表；一行一个“条目 × 来源段”，清单外条目一行一条）**

| 键 | 含义 |
|---|---|
| `id`、`kind`、`source_id` | 条目编号、`third_party`/`extra`、来源编号 |
| `dim.<维度 id>` | 维度值 |
| `name`、`features` | 名称、特征（清单外条目必填 `name`） |
| `unit` | 本次单位（必填） |
| `quantity_name`、`ours_note` | 本次数量项名、本次说明 |
| `确认量`、`规则推算量`、`方案暂估量`、`未决量` | 本次各层级数量；项目列名常是“确认”“规则推算”等，在 `columns` 里映射 |
| `total`、`estimate_dominant` | 可选，写了就核对 |
| `row_id`、`seq`、`code`、`row_name`、`row_features`、`row_unit`、`row_quantity` | 本段只有一条来源行时，直接写在这里；`row_name`、`row_features`、`row_unit` 没写时取 `name`、`features`、`unit` |
| `tp_quantity`、`tp_unit` | 来源段数量和单位；没写时取 `row_quantity`、`row_unit` |
| `difference`、`difference_rate`、`conclusion`、`disposition_note` | 差额、差额率、结论、处置说明 |
| `third_party_corrected`、`correction_note` | 修正标记和说明 |
| `unit_mismatch_note`、`quantity_note`、`missing_drawing_note` | 见第 5 节 |
| `search_drawings`、`search_targets`、`search_method`、`search_hits`、`search_unread`、`search_uncovered`、`search_record_ref`、`search_note` | 检索依据各项（`search_note` 是文字说明） |
| `redirect_to` | 去向条目编号（多值）；也可以用 redirects 表 |

同一 `id` 出现多行时，每行是一个来源段（每个来源一行），条目级的键（维度、本次量等）各行必须相同，不同则报错。一个来源段对应多条来源行时，用 **source_rows** 表（键：`item_id`、`source_id`、`row_id`、`seq`、`code`、`row_name`、`row_features`、`row_unit`、`row_quantity`）列全，items 表里该段的单行键留空。

**detail_rows（明细表）**：`id`、`item_id`、`level`、`quantity`、`unit`、`basis`、`area`、`drawing`、`locator`、`relation`、`note`、`dim.<维度 id>`、`aggregation`、`aggregation_reason`、`member_keys`（多值）、`member_quantity_name`、`member_table`、`excluded`（是否列）、`excluded_rule_ref`、`excluded_issue_id`、`excluded_note`。

- `excluded` 为真时，后三列合成该行的 `excluded` 对象（5.1 节）。
- `excluded` 为假或空，而后三列有值的，报错。

**redirects（去向表）**：`item_id`、`target_item_id`，可选 `source_id`（多来源时指明是哪一段的去向，单来源可省）。

**issues（问题表）**：`id`、`handler`、`nature`、`common_issue_id`、`rule_ref`、`plugin_issue_ref`、`title`、`text`、`impact_text`、`current_practice`、`current_option`、`dim.<维度 id>`（多值）、`source_refs`（多值）、`status`、`group_id`。`handler`、`nature` 用 `value_maps` 把项目的叫法映射到代码。

**issue_links（问题关联表）**：`issue_id`、`item_id`。**issue_sources（问题原条目表）**：`issue_id`、`ref`、`text`。**issue_impacts（问题影响表，可选）**：`issue_id`、`value`、`unit`、`note`，一行一段，同一问题多行即多段。

**common_issues（共性问题表，可选）**：`id`、`nature`、`question`、`text`、`handler`、`current_option`、`rule_ref`、`status`、`dim.<维度 id>`（多值）。

**issue_options（做法表，可选）**：`issue_id`（共性问题或个别问题的编号）、`option_id`、`text`、`value`、`unit`、`note`。一行是一个做法的一段影响；同一做法有几段影响写几行，`text` 各行相同；没有影响量的做法写一行，`value` 留空、`note` 写“现做法”或说明。

**common_issue_links（共性问题直接挂条目，可选）**：`common_issue_id`、`item_id`。

下面两张表（member_links、detail_aggregation）用于“按列取层级、从挂接表取数量”，本轮做（用户 2026-10-15 放行，对应登记 E5 的台账下钻）。

**member_links（成员挂接表，可选）**：`catalog_key`、`detail_id`、`quantity_name`、`level`、`quantity`。一行表示“这个成员的这个数量项计入这行明细”：
- 成员对象没有这个数量项（同名、同层级）时，按本行补上，单位取明细行的单位；已有而数值不同的报错，不猜；
- 成员补进该明细行的 `member_keys`；
- 同一成员同一数量项挂进几行明细的，仍按 C3-4 要写拆分份额。
- 这样逐回路台账可以按“回路表 + 挂接表”两张表接入：回路表只建对象（属性、维度），数量和层级从挂接表来。

**detail_aggregation（明细汇总方式表，可选）**：`detail_id`、`aggregation`、`aggregation_reason`、`member_quantity_name`、`member_table`（可以用 `constants` 补）。给明细行补汇总方式，免得改明细表；与明细表里已写的不同时报错。

映射的 `comparison` 里写的 `thresholds`、`legacy_search_evidence` 原样带进视图。

**members（成员台账表，可选；每行成为一个对象）**：`catalog_key`、`object_id`、`detail_id`（挂到哪行明细，会补进该行的 `member_keys`）、`title`、`category`、`status`、`professional`、`detail`、`source`、`dim.<维度 id>`；数量列在映射里声明 `"quantities": [{"name": "水平长度", "unit": "m", "level": "规则推算量", "column": "H"}]`，属性列声明 `"attributes": {"起点箱": "box"}`。这样建的对象是 `unlocated`；`catalog_key` 与 `--base-view` 里已有对象相同的，不新建，改为引用已有对象（保留其回图坐标）。

## 13. 用户答复（2026-10-15）

1. **“一致”怎么判**：用户最终答复（问题收集会话转达）：“第 1 项我选：页面可设容差，默认计量 ±5%、计数必须相等。”
   - 默认带宽按单位类别分写：计量 ±5%，计数须相等。生成器按默认值判，不由专业逐条判。
   - 页面上可以自设容差，按容差重新显示一致、多算、少算，见 5.4 节。
   - 用电气现有数据试过：计量 ±5%、计数须相等时，与电气现有结论完全相同。若全部单位统一 ±5%，会有 11 条（套、个）由多算或少算变为一致。
2. **多来源**：有多个第三方时并排。一个条目带多个来源段，见 5.3 节。
3. **导出**：先不做，需要时由模型直接生成 Excel。
4. **金额影响**：不考虑价格，只算量。单价、`priced`、`amount_impact`、按金额排序全部删除。
5. **20 MiB 分页**：取消。20 MiB 是在线上传的上限，不是页面容量上限；在线上传已停用，页面不设上限、不分页（第 11 节）。

## 14. 页面要点

第五处修改后的页面按下面写（用户 2026-10-15 看 97a7859 样页时的意见：成果和对照审核看不出大的区别；明细看不到；“关系”“定位”“成员”看不懂；分包筛选是一串英文；逐条审核会产生重复和矛盾的意见；重点是成果中没有依据或无法判断的内容）。

- **模式**（有 `comparison` 时，按下面顺序排列）：
  1. **成果**（默认，用户选定）：本次有量的条目，按分类列好。
     - 按 `overview`（楼栋）、`section`（分部）、`category`（品类）三级分类。只列本次合计不为 `null`、0，或有未决量的条目，含清单外新增；本次量为空的（图上无、归入他项、缺图）不列在这里，分别在对照审核和待解决问题里。
     - 有已定不计的条目，行上标“另有已定不计”和不计的量。
     - 成果末尾单列一组“已定不计”，默认收起，按楼栋列出有已定不计明细的条目，包括本次合计为 0 的。每条显示不计的量、依据和说明；依据是口径决定单或已关闭的问题，可以跳转。这一组不计入欠缺计数，也不进待解决问题。
     - 每行：名称和特征（不显示内部编号）、单位、本次各层级数量和合计。依据状况条分三段：有依据（确认 + 规则推算）、估算（方案暂估）、待定（未决）。挂着未答复问题的，按性质显示标记，点了跳到该问题。第三方数量和结论在行尾作一列对照，不作排序依据。
     - 分类标题显示条目数、含估算的条数、有待定的条数。不跨条目求和。
     - 筛选：范围（全部 / 有清单对应 / 清单外新增）、依据状况（全部有依据 / 含估算 / 有待定）、问题性质、`filter` 维度，以及全文搜索。`technical` 维度不进筛选。
  2. **待解决问题**（原“欠缺条件与资料”）：成果中没有依据或无法判断的内容，是页面的重点。
     - 按问题性质分 8 组（6.1 节），组标题写这一类要什么样的答复。组内先列共性问题，再列没归进共性问题的个别问题。
     - 共性问题一行：问法、处理方、现做法、适用范围（个别问题数、条目数、涉及楼栋）、答复状态。点开：情况；各做法并排列出影响量，标出现做法；适用范围清单（个别问题和条目按楼栋分组，条目显示本次各层级数量）；答复区（9.1 节）。
     - 个别问题挂了共性问题的，显示“已按共性答复”或“待共性答复”，只能设例外；单独成立的照问题批注答复。设了例外的显示“此处已设例外”和本处意见，例外过期的显示“此处原设的例外已过期，须重新核对”，例外处于意见冲突的显示“例外意见冲突”（9.1 节）；条目同样。
     - 成果里含估算或待定、却没挂任何问题的条目，以及本次依据不足的偏差没挂问题的，单列“没有依据、也没挂问题”（C3-9），提醒专业补挂。个别问题没写性质的放“未分类”。
     - `closed` 的默认收起。有现有问题组时，提示“另有 N 个图面问题组待复核”，可以跳到图面复核。
     - 末尾单列一组“检索记录不全”，默认收起，只作提示（第 5 节）。
  3. **对照审核**：与第三方数量的偏差，按 5.5 节归因，不再逐条审。
     - **清单的问题**：按类型分组（清单少计、清单多计、清单漏量、清单列了图上没有的、清单规格写错），每组是一条隐含共性问题，整组答复一次。组内列条目、清单量、本次量、差额；`both` 的标“部分是清单的问题”并显示 `excess`。
     - **本次依据不足**：按所挂的共性问题或个别问题分组，点了跳到待解决问题里答复；没挂的列“依据不足的偏差未挂问题”。
     - **无法归因**（单位不同等）、一致、归入他项各单列，默认收起，只作查看；归入他项可以跳到去向。
     - 条目上没有快捷结论按钮，只有“设为例外”。页面容差照旧只改显示（5.4 节），不改归因。
  4. **图面复核**：现有的问题组和对象（原“复核”）。
  - 默认打开成果；没有条目时打开待解决问题（`comparison` 只有问题时）；两者都没有内容而有问题组时打开图面复核。
  - 原“清单外新增”并进成果，用“范围”筛选；`#mode=extras` 打开成果并筛到清单外新增。
  - 没有条目时不显示“成果”；没有对照条目时不显示“对照审核”；没有对象和问题组时不显示“图面复核”；待解决问题始终显示（为空时写“没有待解决的问题”）。
- **顶部**：
  - 先是待解决计数：按性质列未答复的共性问题和单独成立的个别问题数，再加“没有依据、也没挂问题”的条目数。点了进入待解决问题对应分组。检索记录不全不计入。
  - 有对照条目时，下面一行是一致带宽的默认规则和页面容差设置（5.4 节），以及“差异超阈值”的当前百分比。
- **总览**：按 `overview` 维度出卡片，另有“全部”。每张卡片依次显示：
  - 成果条目数（含清单外条数）、含估算的条数、有待定的条数；
  - 待解决问题数（按性质）；
  - 对照：清单的问题条数、本次依据不足的偏差条数、各结论计数（按页面显示的结论）。多来源时按当前对照来源算。
- **对照审核的组内列表**：每行显示名称和特征、单位、清单量 → 本次合计、差额和差额率、结论（按页面容差显示，与数据结论不同的标“原：…”）、归因；多来源时每个来源一列。组内按差额率绝对值排序，也可以按差额或编号。可以按差异超阈值、结论、来源间结论不一致、检索记录不全和维度筛选。
- **条目详情**（成果里）：
  - 标题：名称、特征、楼栋、分部、品类。
  - 本次成果：各层级数量与合计，依据状况。
  - 明细组成与依据：楼层区域、层级、数量、依据（计算式和图纸）。`relation` 不是“对应”时作标签显示（如“清单外新增”“对应-修正”）。`locator`、`note` 和 `technical` 维度（如计算包号）收进“技术来源”，默认收起。
    - 已定不计的行排在计入的行之后，标“已定不计”，显示原层级、数量、依据和说明，不进层级合计。
  - 有成员的明细行有“下钻”，按钮用成员台账的 `title`（电气叫“逐回路台账”）。有定位的成员在图面上高亮，可以上一处、下一处（第 8 节）。
  - 没有明细的条目不显示空表，写明原因：图上无（附检索依据，不全的标“检索记录不全”）、归入他项（附去向，可跳转）、缺图（附缺图说明）。
  - 挂在本条目上的个别问题和共性问题，按性质列出，可以跳过去。
  - 对照：各来源的行（修正的附修正说明）和归因。
- **对照审核里的条目详情**：先列第三方的行、差额和归因，再列本次成果。
- **个别问题详情**：情况、影响、现做法（有做法的并排列出）、涉及量（挂接条目已有的数，不跨条目求和）、原条目原文；可以跳到楼栋、条目、问题组和所属共性问题。
- **审核意见**：共性问题、个别问题、条目三级，继承与例外见 9.1 节。
- **保存**：只有本地保存。
