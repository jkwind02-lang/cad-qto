# 协调台账与交付接收执行契约

本入口消费已识别、已计算的专业成果，不重算工程量、推定归属或代替裁决。工作包表示对象、范围和数量责任，不自动创建代理。现有最小成果JSON的缺插件使用节仅提醒的兼容行为保持不变；新增协调交付门缺少来源证据时返回未核，不表示工程数量验收。

## 共同CLI与退出码

两宿主均可运行 `python skills/qto-coordinator/scripts/qto_coordination.py <子命令> --input <JSON> --out <回执JSON>`。子命令为 `init`、`delivery`、`handoffs`、`collect`、`backflow`、`hook-plan`。PASS退出0，FAIL退出2，UNVERIFIED退出3；任一FAIL优先于未核。回执含逐项发现及 `engineering_acceptance=false`。只看进程运行成功不足以判断业务通过。

`init`另需 `--out-dir <新目录>`；`collect`另需 `--state-dir <收件工作区>`。除初始化拒绝覆盖既有目录，运行回执和收件状态可原子更新，输入不得作为输出覆盖。路径相对请求文件解析；嵌套基准来源相对其基准文件解析。文本用UTF-8。

## 参数化初始化

输入 `qto-coordination-init/1.0`：`project_id`、显式 `capabilities` 字符串数组、`packages` 数组。每个包至少有 `package_id`、`skill`、`actual_scope`、`responsibility`，skill须属于输入能力。未知范围的包不建立，数组可空并返回INPUT_REQUIRED就绪状态。能力数量、业务专业、区域和包数全部来自输入。

输出中文协调配置、跨包对账模板、问题收件输入和项目触发适配模板。模板含未知路径/null时尚不能通过对账，不生成工程量，也不调用CAD抽取或启动会话。

## 数字成果交付清单

输入 `qto-delivery-manifest/1.0`，含 `package_id`、布尔 `has_numeric_results`、`artifacts`。每个文件为 `{role,file,sha256}`，sha256为完整64位小写指纹。数字成果默认要求 `summary`（用户可读汇总）和 `html_review`（HTML复核页）。汇总可用Markdown、TXT、CSV、XLSX或PDF；检查文件存在、非空及支持格式的可读性，不证明表内专业数据或视觉布局已核准。PDF用可用的pypdf解析实际页面和内容流；伪文件、截断或不可解析内容为FAIL，解析依赖不可用或需密码时为UNVERIFIED，不凭扩展名/PDF头通过。损坏XLSX转为artifact_unreadable及业务FAIL回执。HTML须可解码且有HTML文档结构。纯诊断无数字不误要求数量交付。

`waivers`按角色索引，每项须有 `actor:"user"`、`at`、`quote`、`scope:{package_id,roles:[角色]}`、`source:{file,sha256}`。引用文本须真实包含用户原话并命中本包本角色。项目格式漏列、助手自述或无来源的“免交”均不能自动豁免。

`plugin_usage`复用《通用成果字段与状态》中的“插件使用与临时处理”结构（插件版本、提交、换版、记录六列），新增每行唯一 `row_id` 以便溯源。登记文件名通过 `registrations:{文件名:{file,sha256}}` 核对真实原单；“待协调登记”为未核，须收件后回流；“不进插件：理由”保留项目判断；“无”不得与具体卡点或方法替代并存。`method_replacements`须逐项关联 `usage_row_id`，反向核对表内没有写“无”。`local_scripts_present`只提醒，不据此推定绕过插件。

正式来源用 `source_mode:"released"` 和 `release_source:{file,sha256}`，文件schema须为 `cad-qto-release-source/1.0`，以 `business_version/source_commit` 核对实际使用版本。中途换版用 `additional_release_sources`补齐来源，逐份复用相同schema、业务版本及完整提交号核验。只核对所附发布记录和使用声明，不冒称当前宿主安装已核。

未发布开发验证单列 `source_mode:"development"`、`development_source:{baseline_commit,business_version,files:[{file,sha256}],source_fingerprint}`，`plugin_usage.development_source_fingerprint`须一致。源码集合按file排序后，用不转义中文、键排序、紧凑JSON序列化，再取UTF-8 SHA256。基线提交为40位小写提交号；使用记录的提交填写该基线。逐文件实核指纹并回 `DEVELOPMENT_VERIFIED_NOT_RELEASED`。开发源不生成发布记录，不表示已发布、已安装或已完成交叉复测。

## 全部数量工作包接收与唯一出口

输入 `qto-package-reconciliation/1.0`：

```json
{
  "schema": "qto-package-reconciliation/1.0",
  "project_id": "匿名工程",
  "packages": [
    {"package_id":"区域甲","skill":"qto-electrical-routes","result_file":"区域甲成果.json","result_sha256":"完整SHA256"},
    {"package_id":"区域乙","skill":"qto-electrical-routes","result_file":"区域乙成果.json","result_sha256":"完整SHA256"}
  ],
  "baseline":{"file":"完整编号基准.json","sha256":"完整SHA256"},
  "handoffs": []
}
```

每个实际成果文件用 `qto-package-quantity-rows/1.0`，含 `package_id`、`source_revision`、`source_fingerprint`、`rows`。每行有唯一 `row_id`、`physical_id`、明确 `quantity_type`、`unit`、`basis`、`actual_scope`、`quantity`、布尔 `included`、原编号 `source_ids`。资料指纹必须为64位SHA256。数量未知用null，不填写0。仅included=true的行参与数量出口。

`actual_scope`为非空、不重复的实际段标识数组，按实际对象位置/段界表达，顺序不影响身份。例如 `['A楼/一层/回路L1/实际段S1']`，不能只填提出包名或接收包名。不同文字是否实际指向同一段仍须上游统一事实ID，检查器不做几何推断。`basis`为实际计量口径，如“设计路径平面长度，不含竖向”，`quantity_type`可为 `cable_plan_length`，单位为 `m`。清单项/清单外新增另写 `accounting_class`，不能借分类不同隐藏重复。

每条交接至少含 `handoff_id`、`proposer_package`、`receiver_package`、上述七项复合身份（物理对象、数量类型、单位、口径、实际范围、资料版本和指纹）、`quantity`（可null）、`proposal_evidence`、`status`。已接收必须 `status:"accepted"` 并有 `receiver_row_id` 和 `receiver_result_sha256`。实际文件SHA、包号、真实计入行、全套身份逐项一致才接受；已知交接量还须与实际接收行相等。只有声明或只有数量相等均不通过。待收/拒收/转裁决保留未决；本包移交后仍计同范围报重复。

相同复合身份的多出口报冲突。同一物理对象和数量类型的实际段重叠时，单位、自由文本口径或版本不同也报口径冲突，须先明确互斥对照/资料适用范围；不启动单位换算或替项目选方案。不同数量类型（箱体与电缆）、真正互斥实际段可并存。对照方案应明确 `included:false`，不可混进当前数量出口。

完整编号基准文件用 `qto-quantity-universe/1.0`，包含布尔 `complete`、真实设计/清单 `source_documents:[{file,sha256}]`、`items`。每个item含原 `source_id` 和同一复合身份。完整且来源指纹有效时逐原编号检查0出口、多出口、无出处编号、出口丢原编号和身份不一致；复用 `qto_review_statistics.build_coverage_check`核对显式基准与实际行的覆盖关系。只核对输入所声明的完整基准，不证明上游提取设计/清单已经无遗漏。

同一原编号跨真实段合法拆分时，在每个基准分项明确 `relationship:"split"`、`split_basis`，复合身份除actual_scope外一致且各实际段互斥；接收行保留同一个原source_id。基准自身同物同数量类型范围重叠报歧义，不能靠写进两条基准使重复合法化。缺基准、来源、完整声明时标全量未核，不能从成果里已经出现的ID反推没有漏计；已显式列出的0/多出口仍报告。

## 幂等收件、原始登记与回流

`qto-plugin-issue-intake/1.0`输入有 `project_id`、`host`（Claude/Codex）、`packages:[{package_id,usage_file,usage_sha256}]`。usage_file是真实交付清单文件，收件读取其中“待协调登记”行，以项目+涉及Skill与插件脚本+具体卡点原文形成问题签名，保留所有包/行ID/规范化真实来源路径/原文件SHA/使用版本。相同包、行和内容来自不同规范化来源路径时保留两条来源；同一真实文件重复收件仍幂等。问题描述相似不自动语义合并。

默认在指定收件工作区的“隔离维护演练/问题登记/待处理”真实调用现有 `register_plugin_issue.py`，不用正式队列练习。只有明确提供 `--maint-dir`才使用该既存维护队列；不从安装位置猜测。登记正文使用真实模板必需字段，原单包含收件签名和来源；回执必须能找到真实原单，不能只造一条收件记录。匿名演练须维持默认隔离目录，不能进入正式登记队列。

若已有同一卡点原单，显式提供 `existing_registrations:[{signature,file,sha256,match_evidence}]`，原单须在本次明确维护目录的问题登记中，且包含同一Skill、卡点和逐字依据；通过后关联该原单，不另登。登记工具和收件层不自动裁定两条相似问题相同。

收件用操作系统文件锁串行同工作区；进程终止后锁由系统释放。真实登记已写、收件回执未写时，重试在原单恢复签名，不重复登记。原单搬至问题登记子目录可找回；原文必须保持冻结前缀，维护追加允许，前缀篡改/原单消失会失败。收件JSON保留全部来源行与受影响包；回流分列处理版本、actual_rerun、复跑凭据和待人工动作，发布或代码修复不自动标项目已复跑。

`backflow`消费 `qto-plugin-issue-backflow/1.0`。若标 `actual_rerun:true`，真实JSON凭据必须为 `qto-project-rerun-receipt/1.0`，匹配project_id、processing_version和全部affected_packages，status=PASS，并有真实执行 `executions:[{command,exit_code:0}]` 及有SHA的 `output_artifacts`。此处核对凭据和文件一致性，不冒称本校验器重新执行了专业复跑。

## 可选宿主触发适配

`hook-plan`只检查项目模板 `qto-project-hook-plan/1.0`，模式off/test/on，限定project_id/project_root。on必须显式on_since和允许的新会话eligible_session_ids；不热改存量会话。输出 `applied:false`、`global_config_changed:false`、`host_loading_verified:false`。不为宿主发明接口，不修改全局配置；真实宿主钩子安装/加载属于另行适配验证。共同CLI是当前可执行路径。

本入口不修改项目专属归属、不将原项目临时处理计为插件修复，也不做发版、安装、增版本、推送或交叉宿主复测。
