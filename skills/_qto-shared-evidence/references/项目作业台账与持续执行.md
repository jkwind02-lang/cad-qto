# 项目作业台账与持续执行

## 适用情形与职责

多图、多系统、多专业、长任务或需要接收复核意见后重算时，用项目文件保存实际进度。单一专业仍由该专业主责，可直接使用本执行器；不因使用作业台账就扩大为全专业任务。一次简单尺寸核算可直接调用专业工具。

台账围绕人工算量的七个动作组织：确定范围、读图认识工程、沿系统识别、分段测量、应用规则、换顺序回图、整理交付。模型负责理解图纸和项目规则、建立工程对象和有来源的工作输入；程序运行已有几何与专业计算器；资料缺失、无法裁决的设计冲突、计量选择和正式采用由真实项目决定。工作识别无需逐对象向用户请示。

先读所属专业 `SKILL.md`，再按需查[各专业持续算量执行路径](各专业持续算量执行路径.md)。不得为了建立台账先要求用户手工填完识别清单。

## 1. 建立一次任务，随后持续恢复

从插件根目录运行；示例路径需替换成当前实际项目目录：

```bash
python skills/qto-coordinator/scripts/qto_workflow.py init \
  --workflow /project/takeoff/workflow.json --state /project/takeoff/state.json \
  --project-id project-A --task-id takeoff-001 \
  --scope "三层给水系统，本轮包含平面及相关系统详图" \
  --source /project/sources/water-plan.dxf --skill qto-pipe-networks

python skills/qto-coordinator/scripts/qto_workflow.py next \
  --workflow /project/takeoff/workflow.json --state /project/takeoff/state.json
```

`init` 只建立已明确专业的读图、准备输入、程序计算、回图检查骨架。骨架没有预填对象、工程量或完成结论。来源必须是真实文件；程序不会把“可能涉及某专业”当成已确认构造。

**持续执行循环：**

1. `next` 读取实际文件，返回可推进任务、任务指纹、输入输出编号、缺失事实及受影响量项。
2. 对 `actor=model`，读取必要局部资料，完成真实模型工作产物；按新发现对象、必要图种和共享事实用 `amend` 更新台账。
3. 模型产物形成后用 `record --task ... --actor model --note ... --expected-task-fingerprint ...` 记录。指纹应来自开始这次工作时的 `next`；条件变化后先重读，不给旧解释补一个当前指纹。
4. 对 `actor=program` 用 `run --task ...`，或 `advance --max-jobs 8` 连续推进当前可运行的登记工具。程序任务不能由 `record` 伪装完成。
5. 某一程序运行失败，保留错误和原结果；模型修输入，其他独立工作继续。模型任务和真正项目决定不由程序跳过。
6. 再读 `next`，直到当前范围无可继续的取证/计算工作；输出剩余缺口及其实际影响。不能在尚有可处理任务时只交台账让用户代做。

上下文压缩或会话恢复时用 `resume`；它重新核对真实文件和工具身份，不相信手写的 `completed`。重新建立 `task_id` 表示新的任务；`--mode independent_assessment` 用于独立复测，不能继承旧生产任务的判断或状态。

## 2. 按人工底稿建立对象、应计量项和实际出口

`workflow.json` 使用 `qto-project-workflow/1.0`。主要集合如下：

| 集合 | 对应的实际工程工作 |
|---|---|
| `artifacts` | 源图、规则、读图记录、共享事实、计算输入、原生结果和复核文件；每项有真实路径 |
| `scopes` | 楼层/区域/系统/图种范围，有来源依据、必要任务和实际索引 |
| `work_packages` | 单一主责专业及其范围；共享事实只保存一份并声明消费关系 |
| `tasks` | 读图、识别、计算、对账、复核和交付动作，明确角色及文件输入输出 |
| `objects` | 工程实物及多图观察的对应，例如一面墙、一段管网、一个设备实例 |
| `observation_dispositions` | 实际图元观察被用于计量、只作证据、容器、排除还是尚未处理 |
| `quantity_targets` | 本范围预期应该计算的量项，包括单位、口径、方案、几何/项目规则/采购参考角色 |
| `quantity_claims` | 量项绑定的真实计算器结果文件和 JSON Pointer，不填一个手抄数字替代 |
| `issues` | 已尝试的取证、未决事实、影响任务与量项、问题组和解决产物 |
| `review_bindings` | 复核页面对象与量项对应；同一实物的证据图不再输出第二份数量 |

一面墙可以有墙体净体积、两侧不同做法面层、踢脚长度等多个应计量项；它们共享实物身份，保留各自专业、层、侧别和计量口径。一个设备在平面、系统图和大样中出现多次，是多份观察，不自然等于多台设备。

最小原生结果绑定示例（字段和值均须来自本次实际计算）：

```json
{
  "id": "wall-volume-claim",
  "target_id": "wall-A-net-volume",
  "artifact_id": "masonry-result",
  "result_pointer": "/items/0/net_volume_m3",
  "identity_pointer": "/items/0/id",
  "expected_identity": "wall-A",
  "quantity_level": "inferred",
  "owner_work_package_id": "masonry"
}
```

数组行号只负责寻址。经过多层带 ID 数组时，用 `identity_bindings:[{identity_pointer,expected_identity}]` 核对每一层，例如楼层 ID 和楼层内管段 ID；ID 在本层须唯一。无 ID 的分组行用 `record_bindings:[{record_pointer,expected_fields}]` 绑定实际语义字段：点位分组是类别/系统/规格/单位/层级，道路结构层是名称/厚度。其他无 ID 行必须给出足以唯一辨别该行的上下文字段；无法辨别的纯数值数组保持待绑定，不能以当前数字本身作为身份。

`unit_pointer` 和 `level_pointer` 可绑定原生单位及数量层级。原生已声明的单位/层级不能用台账字段覆盖。一个语义量项只能有一个有效数量出口；改单位、换专业所有者不能绕过去重。几何量、项目规则量和采购参考分别汇总；不同单位、口径、方案及层级分别保留。

量项、实物和范围的依据，以及实物关联的观察索引，必须由这份结果的生产任务或祖先任务实际消费。仅给量项增加一个当前文件引用，不代表旧计算已应用该规则；执行上下文发现缺少依据依赖时撤下该有效出口，要求模型补入真实输入链并重算。

### 范围分母及其边界

CAD 范围的 `inventory_artifact_ids` 指向实际工作台索引；观察账从索引真实对象读取，不能只拿已经识别成功的对象做分母。未处置图元、没有有效结果的应计量项、未完成的必要系统图/剖详图任务都会保留在报告。

索引没有证明未加载的外参、缺失图纸或未发现系统已覆盖。`reconciled_declared_scope` 仅指**已声明且有来源的范围**对账闭合，输出始终保留 `engineering_completeness_proven=false`。没有 CAD 的尺寸表复核可有依据地声明 `inventory_disposition=not_applicable`，不借此声称完成原图识别。

同一源观察确实需要拆成不同工程范围时，要有不同 `extent_id` 和来源理由；这仍不等于程序证明几何范围互不相交，报告保留 `disjointness_proven=false`。

## 3. 围绕工程问题局部读图

先建立来源绑定索引，再调用 `cad_scope`，或直接使用共享 `read_cad_scope.py`。查询须包含 `question`，例如“这条支路的管径标注指向哪段管线，附近是否有变径”。

```json
{
  "question": "定位本支路管径标注并查看局部上下文",
  "text_pattern": "DN32",
  "context_padding_raw": 2500
}
```

支持实际边界、对象 ID、实体类型、图层和文字筛选；先摘要，再按对象或游标取详细内容。默认一页 60 个对象、24,000 个 UTF-8 字节，连同元数据及文件引用一起计入预算。完整选中、未选中、无法定位记录及对象详情另存文件，不能把未进入本页的对象当成不存在。显式选中的无包围盒对象仍留在问题队列。

同一索引或查询发生改变，旧游标不能继续。图层文字是定位线索，工程用途由模型结合多图证据解释。当前实现会验证和加载完整 JSON 索引，**预算约束的是给模型的响应量，尚未提供磁盘流式或空间分片索引的内存优化**；大图仍应先限定布局/范围。

## 4. 真实输入、依赖与并行

程序仅允许 `tools` 列出的 22 个工具：13 个专业入口及 CAD 索引、局部读取、管网准备、端点交接、跨图对应、实例要求、依赖复算、复核页生成、反馈读取。参数引用已登记文件编号，不接受任意 shell 命令。

计算清单里实际打开的文件也属于输入。包括源图、实体流、提取元数据、识别台账内的证据、CAD 转换旁证、复核场景底图等，均须登记 `artifacts` 并列入对应程序任务的 `input_ids`。只在清单里写一条路径或哈希、只在范围说明里引用，不能替代实际文件依赖。尚待上游生成的输入可先登记为未来产物。

执行指纹覆盖任务约定、范围及工作包、输入实际内容、依赖产物和工具代码；图纸、规则或解释变化，相关任务及下游失效。未受影响且证据身份完整的工作包保持有效。程序指纹保守地包含共享运行资源和执行器，模型工作指纹还包含所属专业的 Skill 与规则文件；修改这些资源可能使相关模型输入及多个专业程序任务一并需要复验。

一个文件只有一个生产任务；共享事实由一个主责动作更新，下游只读。并行模型/程序工作可以复制同一初始状态为不同 `--state` 文件，使用同一台账和不重叠的输出路径。每个状态文件及实际输出独立加锁，工作台账使用共享执行租约，修改台账需等待正在运行的分支结束。

```bash
python skills/qto-coordinator/scripts/qto_workflow.py merge \
  --workflow /project/takeoff/workflow.json --state /project/takeoff/state.json \
  --incoming-state /project/takeoff/state-branch-B.json
```

同一任务出现两份分叉完成记录时明确报冲突，不按“时间较新”猜测采用。租约文件若因进程异常终止遗留，先核实相关进程已结束再清理；不能删除仍在运行分支的锁来强行写入。

每次程序执行先写独立运行目录，核对输入和任务未变化后发布结果副本；旧结果留存。`.qto-runs` 内的原生结果和附属证据是可复核产物，特别是原生文件引用了其中的 CSV、对象详情或其他结果时，须与项目文件一起保留。不能只复制表面上的汇总 JSON 后删除实际证据。状态恢复同时核对执行附属文件身份。

## 5. 用修改包调整工程理解

模型发现缺少一个系统图任务、改变对象对应或需要新增规则时，准备以下修改包，再执行 `amend --patch /project/takeoff/patch.json`：

```json
{
  "project_id": "project-A",
  "task_id": "takeoff-001",
  "expected_workflow_sha256": "当前台账文件的真实SHA-256",
  "reason": "系统图显示本层另有竖段，补读标高后单独计算，保留已闭合平面量",
  "upsert": {"tasks": [], "artifacts": [], "quantity_targets": []},
  "remove": {}
}
```

`upsert` 的每一行是该编号的完整当前定义；修改观察处置账时传入完整 `observation_dispositions`，不得漏掉未处理观察。修改绑定当前台账哈希，原台账按哈希保存历史；并行分支修改过台账后必须重读并重新整理修改包。

真正需用户决定的问题应先保存已完成的定位/补读产物，在 `issues[].attempt_refs` 引用它们。同一原因用 `cause_id` 归组，逐个保留受影响量项与单位。`missing_source`、`design_conflict`、`measurement_choice` 且已有有效取证尝试才进入项目问题队列；单纯还没读图，继续由模型读取。

## 6. 成果、复核和批量意见重算

`report --output /project/takeoff/progress-001.json` 同时生成机器报告和 Markdown。两者来自同一实际结果索引，列明任务、分单位数量、未处置观察、缺量项、归属冲突及下一步。

有图面对象时，使用既有[HTML交互复核与批注](HTML交互复核与批注.md)契约准备模板。模板说明当前底图和对象位置，数量由 `bind-review` 从台账原生结果绑定。复核页对象 ID 必须对应量项实物；其他视图只作证据。数量变化、对象重定向、规则或依赖变化，旧意见都不能直接套到新版本。

```bash
python skills/qto-coordinator/scripts/qto_workflow.py bind-review \
  --workflow /project/takeoff/workflow.json --state /project/takeoff/state.json \
  --view /project/takeoff/view-template.json --output /project/takeoff/view-001.json
```

正式进入执行链的视图 JSON 须登记为模型 `review` 任务输出，模板和实际结果列入其输入；绑定后按模型工作 `record`。随后登记 `review_html` 程序任务生成现有 HTML。模板也可输出未登记的草稿，但草稿文件本身不构成完成检查点。

收到实际 HTML/JSON 意见后，用 `review_feedback` 程序任务读取当前视图及反馈，生成登记的交接产物，再运行：

```bash
python skills/qto-coordinator/scripts/qto_workflow.py import-review \
  --workflow /project/takeoff/workflow.json --state /project/takeoff/state.json \
  --handoff-artifact review-handoff-001 --output /project/takeoff/review-patch-001.json
```

应用修改包后出现真实执行链：**模型解释意见 → 准备新版原生输入 → 调用原专业计算器 → 回图核对差异及形成回执**。同包意见一起交给模型解释，避免一条意见反复克隆相同计算任务；同一交接文件重复导入不会再建重算任务。

问题组内选中的对象进入该次改算；组内排除成员保留原有效数量出口。新版输入即使仍包含全组，只有明确选中的量项迁移到新版结果。意见如影响未选对象或共享工程条件，模型应追加明确的范围及依据修改，不能静默扩散。

本执行层不自行把文字意见翻译成尺寸或认可量，也不自动提升为正式采用。完成回执应说明采用了哪些意见、保留哪些例外、新旧数量和理由、重新检查的图面，以及剩余未决；用户无需代替模型逐件制作这些工作文件。

## 7. 能力声明

自动完成检查点证明文件执行链闭合，不证明模型已经认识所有工程构造。本轮机制可支持工作解释与候选推算持续推进；专业能力档位、真实图纸识别准确率、项目计量条款适用性及正式采用仍须分别评价。执行器不扩展到造价、单价、采购决策或对外发布。
