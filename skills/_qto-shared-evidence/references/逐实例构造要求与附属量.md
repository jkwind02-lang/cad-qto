# 逐实例构造要求与附属量

适用于模型已经从当前说明、图例、详图和实际对象读取出“什么条件下、哪个实物或接口需要什么附件”的工作计算。模型负责读图解释；工具逐实例执行已解释条件、规格绑定、例外、去重和件数运算，不包含项目经验规则或自动生成专业公式。

先按[模型工作识别记录格式](模型工作识别记录格式.md)建立实际模型工作识别记录；模型的 working/unreviewed 结果不等于人工核定。条款、适用对象、事实、例外和独立安装位均须有本轮文件哈希及图面定位。没有读完的图示附件继续读图，不能以“未登记”为由全部从条款新增。

平面交叉只能先建立穿越候选。套管、封堵或局部保温要求依赖实际三维穿越时，继续核对管道高程处是否存在墙身／板体、穿越类型及敷设方式；不能把平面交墙直接计为已确定套管。现有 `when` 可保存该适用事实为 `null`：输出应设数量未决，同时列明条件成立时的数量影响，既不填零也不当作不适用。湿区楼板、普通内墙、外墙或沉降缝详图分别核适用范围，不能因“都是套管”互套构造尺寸。

## 执行

1. 从当前源条款读出要求与例外，锁定实际范围。逐设备识别独立端口，同一实物不同视图采用同一物理编号；不同端口分别建立主体。
2. 形成下述 JSON 输入，运行 `scripts/qto_instance_requirements.py --input 输入.json --output 逐实例结果.json`。程序以输入目录解析相对文件路径，输出必须使用新路径。
3. 核查每条记录的应设数量、图示已覆盖、规则新增余量、规格、排除和未决。应设数量已经包含已覆盖量，不与其相加。
4. 管网使用专业 `qto-pipe-networks/scripts/merge_pipe_instance_requirements.py --input 合并输入.json --output 合并结果.json`，同时生成同名 Markdown 并逐行核验。原网络和逐实例结果只读；其他专业交给各自计算与交付链。
5. 条款、对象事实或图示归属变化后重算；可给共享脚本增加 `--previous 上次结果.json`，输出新建/变化/移除记录。当前实现全量复算后对比依赖签名，不能声称已经实现增量执行提速。

## 输入合同

Python API：`evaluate(payload, base_dir='.', previous=None)`。版本 `schema: qto-instance-requirements/1.0`。

顶层字段：

| 字段 | 内容 |
| --- | --- |
| `run_id`, `scope_id` | 本轮与声明范围标识 |
| `scope_complete` | 模型对当前声明的对象及要求是否已读完的声明；工具不证明原图完整读取 |
| `sources` | `source_id,document_id,revision,path,sha256,status:'selected'`；同一 document_id 的冲突版本拒绝 |
| `recognition_ledgers` | `source_id,path,sha256`；复用 qto-model-recognition-ledger/1.0，检查来源及证据文件 |
| `subjects` | 实际实例/端口观察列表 |
| `requirements` | 源条款的本轮模型解释 |
| `existing_accessories` | 已画出并已有唯一数量出口的附件，明确与需求对应 |

以下所有 `evidence_refs` 用 `ledger_id:evidence_id`，解析到模型台账中包含文件路径、哈希、原始定位的证据。`recognition:{ledger_id,entry_id}` 必须找到 include 条目，并覆盖该观察或条款编号；不能伪造人工签认字段。事实证据须属于该对象的识别记录。

### 主体

每个 subject 有 `subject_id,physical_id,subject_kind,system,scope_id,identity_anchor,recognition,evidence_refs,facts`。

- `subject_kind` 为 `instance` 或 `port`。端口额外要求 `parent_physical_id,port_key`，普通实例不得夹带 port_key 拆分身份。
- `identity_anchor:{source_id,object_id}` 指原始图元完整实例路径或等效稳定源身份；object_id 必须在对应识别台账的 object_ids 中。两个 physical_id 不能冒用同一源实例/端口。多端口可以分别提供实际端口子对象；若源CAD只能定位到同一个设备块，模型台账 entry 须额外记录 `port_bindings:[{subject_id,anchor_object_id,port_key,parent_physical_id}]`，逐端口与实际识别绑定并随台账哈希冻结。同设备源锚的多个端口只有各自命中绑定、父设备相同且 port_key 不同才可分开计量。只改运行输入的 port_key 不能拆分实例。
- 同一 physical_id 的多视图观察归并，不增加实例数。系统、范围、设备及端口身份冲突拒绝；事实冲突保留 null。
- `facts` 为 `{事实名:{value:标量或null,evidence_refs:[...]}}`。例如 `dn`、器具种类、是否自带附件，均来自实际对象；缺 DN 不套经验值。

### 条款解释

每条 requirement 有 `requirement_id,requirement_key,version,system,scope_id,subject_kind,professional_owner,accessory_type,accessory_role,installation_position,basis,recognition,evidence_refs,when,exceptions,quantity,specification`。

- `accessory_role` 表示实际用途，如隔离、排气等；用当前条款语言一致表达。工具不证明任意自然语言同义词相等，不能通过改写名称规避模型的同物核对。
- `installation_position:{relation:'subject_interface'}` 指本实例/端口对应安装位。同端口同专业用途的条款即使 requirement_key 改名，也共用数量槽。
- 两只串联同型附件必须有不同真实安装位。采用 `{relation:'source_object',source_id,object_id,evidence_refs}` 时，该对象及证据必须绑定同一条款识别来源；一个实际物理安装位不能分配给多个主体。典型详图不能冒充多个实际安装位。
- `when` 是条件数组，数组内为且关系；每项 `{fact,op:'eq'或'in',value}`。条件未知为未决，不能当作 false。空数组表示该条款适用于本系统/主体类型下全部已声明对象，须有确切范围依据。
- `exceptions` 每项 `{when:[条件],reason,evidence_refs}`。例外未知也影响适用结论，不能静默排除。
- `quantity:{mode:'count',per_subject:正整数,unit:'个'等件数单位}` 仅计算有源条款支持的件数。工具没有预设任何“每台几件”。
- 长度、面积、体积、重量及按间距布置不能用该计数常数代算。使用 `{mode:'specialist_measurement',unit,required_facts:[...]}` 形成数量 null 的专业计算待办，保留所有条款需要的事实并集。
- `specification:{dn:{from_fact:'dn'}}` 从该实例事实绑定。确由条款规定的规格可以 `{value,evidence_refs}`，但未知不能用固定规格补齐。

同一物理槽内互斥的规格条款，只由适用条款出量，排除条款仍保留 `clause_evaluations`；多个适用条款数量、规格或对象含义冲突时输出未决，不 first-wins、不求和。

### 已有图示附件

每项包含 `observation_id,physical_id,subject_physical_id,requirement_key,system,scope_id,identity_anchor,recognition,evidence_refs,result_record_id,accessory_type,specification,unit`。

必须是经过本轮识别、具有独立物理身份和已有数量记录的附件。两张图表达同一件采用同一 physical_id；同一 result_record_id 不得归给两件附件。类型、规格或计数单位冲突保留未决，不自动从需求中扣除。既有数量多于条款应设数量时也保留冲突，不负数扣减。

`additional_quantity = required_quantity - existing_count` 保留为兼容字段，其明确含义是 `unmatched_requirement_quantity`（本次输入中未匹配的需求），只对件数、身份及规格一致的记录成立。它不证明未采购或未安装量；`procurement_additional_quantity` 保持 null。未提交或未读完现件匹配时，不能把该字段当新增采购余量。零未匹配表示需求已被当前匹配覆盖，不能解释为该附件不存在或规格已闭合。数量未知使用 null；适用性排除单列“不适用”。已知件数但未知规格时保留件数和“规格未决”，不得从汇总消失。

## 管网合并接口

`merge(payload, base_dir='.')` 输入：

```json
{
  "schema": "qto-pipe-instance-merge/1.0",
  "scope_id": "本次管道专业范围",
  "scope_basis": "图框和实际端口的同范围对应依据",
  "network_id": "原管网编号",
  "network_result": {"path": "原管网结果.json", "sha256": "实际文件哈希"},
  "instance_requirements_result": {"path": "逐实例结果.json", "sha256": "实际文件哈希"}
}
```

合并器只消费 `professional_owner:qto-pipe-networks` 的声明范围；多专业分别出量后由协调器处理归属，不静默忽略其他专业行。现有图示附件的 `result_record_id` 须对应原 `valves[].valve_id`，其 `identity_anchor.object_id` 须等于原阀件的显式 `source_object_id`，并且实际来源哈希一致，该对象仍在原管网模型台账 include 集中。当前通用 builder 从中性图元 record_id 写出 source_object_id，infer 原样传递；原 source_id 仍保留 EV-CAD 证据编号，不能通过剥前缀猜测。已有直接源对象路径 source_id 入口仍可使用。系统、类型、DN、单位另行核验；不得借另一个同规格阀件抵扣。

合并结果保留全部原图示阀附件、块族及候选类型，规则余量另列；原管长、断口恢复、管件组合、跨图竖向和未决摘要也完整保留。新增数量不会补足未知的竖向、支架或保温。`validate_summary(result,text)` 逐行核对逐实例状态和数量、汇总及原网络摘要；它不证明模型识图语义正确，也不替代原有专业成果检查。

## 能力边界

本工具验证声明输入的来源一致、模型工作判读记录、条件逻辑、实际物理身份约束、件数和唯一数量出口。它不会自动阅读全部设计说明，不证明自然语言条款已正确解释，不自动确认 source_object 是真实安装位，也不证明所有应计附属量已经列全。模型须回图查漏，完整范围测试同时核对图示与条款两路来源，禁止把局部附件计算称为完整施工量。
